Web accessibility gives you a lot for free. A <button> is a button, an <h2> is a heading, and the browser builds the accessibility tree from your markup. On native iOS, none of that is automatic once you step outside Apple's stock controls. A ZStack with a tap gesture looks like a button, behaves like a button for sighted users, and is completely invisible to VoiceOver, Voice Control, and Switch Control.

That gap is where almost every iOS accessibility bug lives. This guide walks component by component: what the component actually is, why it breaks, the correct code in both SwiftUI and UIKit, the exact steps to test it on a real device, a checkpoint list you can run during an audit, and the failures that show up again and again.

📱

Test on a real device. The iOS Simulator's Accessibility Inspector is useful for a quick tree check, but it does not reproduce VoiceOver gestures, rotor behaviour, or Voice Control matching. Every finding in an audit report should come from a physical iPhone or iPad.

01 — Accessibility properties: the foundation

Before any component makes sense, you need the five properties every accessible element is built from. Get these wrong and nothing downstream works.

PropertyAnswersVoiceOver saysRequired?
accessibilityLabelWhat is this?"Like, button"Always, for anything interactive
accessibilityValueWhat is its current state?"Volume, 50%"Anything with a changing value
accessibilityHintWhat happens if I activate it?"Double tap to like"Optional — only when non-obvious
accessibilityTraitsWhat role does it play?"button", "heading", "selected"Required on custom views
accessibilityIdentifierHow do tests find it?Nothing — VoiceOver ignores itXCUITest only
The distinction that matters most: label is stable, value is dynamic. A volume slider's label is always "Volume". Its value changes every time the user swipes. Putting the current value into the label means VoiceOver announces "Volume 50 percent" as the name of the control, and screen reader users lose the ability to tell the control apart from its state.
Label vs value in practice
Correct 
// SwiftUI
Slider(value: $volume, in: 0...100)
    .accessibilityLabel("Volume")           // stable name
    .accessibilityValue("\(Int(volume))%")  // changes on every adjust

// UIKit
slider.accessibilityLabel = "Volume"
slider.accessibilityValue = "\(Int(slider.value))%"
VoiceOver announces: "Volume, 50 percent, adjustable"
accessibilityInputLabels — the property most teams miss

VoiceOver users hear the accessibilityLabel. Voice Control users speak it. Those are two different assistive technologies serving two different disability groups, and the words that work for one are not always the words a person would say out loud.

// SwiftUI
TextField("", text: $email)
    .accessibilityLabel("Email Address")
    .accessibilityInputLabels(["Email Address", "Email", "E-mail"])

// UIKit
emailField.accessibilityLabel = "Email Address"
emailField.accessibilityUserInputLabels = ["Email Address", "Email", "E-mail"]
Result: a Voice Control user can say "Tap Email", "Tap E-mail", or the full "Tap Email Address" and all three work. Without input labels, only the exact label string matches.
Hiding elements — two different behaviours

Checkpoints
☐Every interactive element has a non-empty accessibilityLabel
☐Labels describe purpose, not appearance — "Close" not "X icon"
☐Dynamic state lives in accessibilityValue, never in the label
☐Hints describe the outcome of an action and are not duplicates of the label
☐Labels are localised alongside visible strings — not hardcoded English
☐accessibilityInputLabels provided wherever the visible text is long or abbreviated
Common failures
Label contains state: accessibilityLabel = "Volume 50%" — the name changes on every swipe, so the control has no stable identity.
Hint used as label: element has only a hint and no label. VoiceOver focuses it and announces nothing meaningful — hints are not read when a label is absent in some contexts.
Identifier mistaken for label: accessibilityIdentifier = "btn_submit" with no label. VoiceOver reads nothing; the identifier is invisible to it.
Untranslated labels: UI is localised into Hindi but every accessibilityLabel is still English — VoiceOver reads English words with a Hindi voice, producing gibberish.
WCAG mapping
4.1.2 A Name, Role, Value — every UI component must expose all three programmatically.
1.1.1 A Non-text Content — icon-only controls need a text alternative via the label.
2.5.3 A Label in Name — the accessible label must contain the visible text.

02 — Traits: the iOS equivalent of ARIA roles

Traits tell VoiceOver what an element is and how it behaves. Native controls get them automatically. Custom views get nothing until you assign them, and a custom view with no trait is announced as plain text — the user never learns it can be tapped.

⚠️

.accessibilityTraits() replaces the existing trait set. .accessibilityAddTraits() adds to it. Using the first on a Text silently strips .isStaticText. Default to addTraits unless you deliberately want to wipe the set.

Replaces — loses isStaticText 
Text("Section Title")
    .accessibilityTraits(.isHeader)
Adds — keeps everything 
Text("Section Title")
    .accessibilityAddTraits(.isHeader)

accessibilityRepresentation — custom visuals, native behaviour

When a control is visually custom but functionally standard, you do not have to rebuild its accessibility from scratch. accessibilityRepresentation swaps in a real native control for the accessibility tree only — the screen still shows your design.

CustomSliderShape(value: $value)
    .accessibilityRepresentation {
        Slider(value: $value, in: 0...100)
            .accessibilityLabel("Volume")
            .accessibilityValue("\(Int(value))%")
    }
// Screen: your custom shape
// VoiceOver: a real Slider — swipe up/down works, no manual adjustable action needed
How to test
  1. Turn on VoiceOver (Settings → Accessibility → VoiceOver, or triple-click the side button if you set the shortcut).
  2. Swipe right through the screen. Every element that looks tappable must announce a role — "button", "link", "adjustable". Silence on the role means the trait is missing.
  3. Open the rotor (two-finger twist), select Headings, swipe down. If nothing is listed, no .isHeader traits exist on the screen.
  4. Check any static text that is styled to look like a link or button. If VoiceOver says only the text with no role, sighted users and VoiceOver users are seeing two different interfaces.
  5. Open Xcode → Open Developer Tool → Accessibility Inspector, target the running app, and inspect the element. Confirm the Traits row matches what the element actually does.
Checkpoints
☐Every custom tappable view carries .isButton or a more specific trait
☐Section titles carry .isHeader and appear in the rotor's Headings list
☐Selected items in a set carry .isSelected, and it updates when selection changes
☐accessibilityAddTraits used instead of accessibilityTraits unless replacement is intended
☐No decorative element is given .isButton
Common failures
No trait on custom control: a styled HStack that opens a screen announces as plain text. The user never knows it is actionable.
Wrong trait: .isButton on static text. The user double-taps, nothing happens, and they assume the app is broken. Worse than no trait at all.
Header trait missing app-wide: rotor Headings is empty on every screen, so there is no way to skim. This is a direct 1.3.1 failure.
Stale isSelected: trait is set once at build time and never updated, so VoiceOver announces two tabs as "selected" simultaneously.
WCAG mapping
4.1.2 A Name, Role, Value — traits are how role is exposed on iOS.
1.3.1 A Info and Relationships — heading traits convey document structure.

03 — Headings

What it is: a text element marked as a section title so VoiceOver's rotor can list it.
Why it matters: a sighted user skims a screen in under a second. A VoiceOver user without headings has to swipe through every single element in order. On a settings screen with forty rows, that is forty swipes to reach the bottom section. Headings turn that into three.

On the web, <h1> through <h6> do this automatically. On iOS there is no heading element at all — a title is just a Text with a bigger font until you tell the system otherwise.

Looks like a heading, is not one 
Text("Notification Settings")
    .font(.title2)
    .bold()
// VoiceOver: "Notification Settings"
// Rotor → Headings: empty
SwiftUI 
Text("Notification Settings")
    .font(.title2)
    .bold()
    .accessibilityAddTraits(.isHeader)
// VoiceOver: "Notification Settings, heading"
// Rotor → Headings: listed ✓
UIKit 
titleLabel.accessibilityTraits = .header
// Note: UIKit uses .header, SwiftUI uses .isHeader
💡

iOS has no heading levels the way HTML does. There is no .isHeader(level: 2). VoiceOver announces every header trait identically. If a screen genuinely needs hierarchy, convey it through the text itself and through grouping — do not try to fake levels with traits.

How to test
  1. Turn on VoiceOver and open the screen.
  2. Two-finger twist to open the rotor. Rotate to Headings and lift your fingers.
  3. Swipe down repeatedly. VoiceOver should jump between each section title on the screen.
  4. Compare against what you see. Every visually distinct section title must appear in that list. Anything missing is a finding.
  5. Also confirm the reverse: nothing that is not a section title should appear as a heading.
Checkpoints
☐Every screen has at least one element with the header trait
☐Rotor Headings navigation reaches every major section
☐Navigation bar titles are announced — usually automatic, verify on custom nav bars
☐Heading text is descriptive, not "Section 1"
☐Body text and captions do not carry the header trait
Common failures
No headings anywhere: by far the most common iOS finding. Rotor Headings is empty on every screen of the app.
Custom navigation bar title not exposed: teams replace the system nav bar with a custom HStack and forget the trait, so the screen has no announced title.
Everything is a heading: the trait applied to every Text in a list, making the rotor as useless as having none.
WCAG mapping
1.3.1 A Info and Relationships — section structure must be programmatically determinable.
2.4.6 AA Headings and Labels — headings must describe the content that follows.

04 — Buttons

What it is: a control that performs an action in place, as opposed to a link that navigates.
Why it matters: buttons are where custom design work happens most often, and every custom implementation is a chance to drop the trait, the label, or the activation gesture. A button that a VoiceOver user cannot activate is a dead end in the middle of a task flow.

Rule one: use the native Button whenever it is possible. You get the trait, double-tap activation, Switch Control scanning, Voice Control matching, and Full Keyboard Access support without writing a line of accessibility code.

Icon-only buttons

An icon with no visible text has no label source. SF Symbols do not provide one — VoiceOver falls back to reading the symbol name character by character, which produces "heart dot fill" instead of "Like".

Reads the SF Symbol name 
Button(action: likeTapped) {
    Image(systemName: "heart.fill")
}
// VoiceOver: "heart dot fill, button"
SwiftUI 
Button(action: likeTapped) {
    Image(systemName: "heart.fill")
}
.accessibilityLabel("Like post")
// VoiceOver: "Like post, button"
// Voice Control: "Tap Like post" ✓
UIKit 
likeButton.setImage(UIImage(systemName: "heart.fill"), for: .normal)
likeButton.accessibilityLabel = "Like post"
Custom views used as buttons

This is the single most damaging pattern in native iOS. A styled container with .onTapGesture works perfectly for a sighted user with a finger and fails for every assistive technology at once.

Breaks VoiceOver, Switch Control, and Voice Control 
ZStack {
    RoundedRectangle(cornerRadius: 10).fill(Color.blue)
    Text("Buy Now").foregroundColor(.white)
}
.onTapGesture { buyNow() }

// ✕ VoiceOver double tap does nothing
// ✕ Switch Control cannot reach it
// ✕ Voice Control "Tap Buy Now" does nothing
// ✕ No .isButton trait
Wrap the same visual in a Button 
Button(action: buyNow) {
    ZStack {
        RoundedRectangle(cornerRadius: 10).fill(Color.blue)
        Text("Buy Now").foregroundColor(.white)
    }
}
// Label inferred from the Text — "Buy Now, button"
// All assistive technologies work ✓
Repeated buttons need context

A list of ten products with ten "Delete" buttons gives a VoiceOver user ten identical announcements. In the rotor's Buttons list they are indistinguishable.

// SwiftUI
Button("Delete") { delete(item) }
    .accessibilityLabel("Delete \(item.name)")
// "Delete Blue Shirt, button" / "Delete Running Shoes, button"

// UIKit
deleteButton.accessibilityLabel = "Delete \(item.name)"
💡

Keep the visible word at the start of the accessible label — "Delete Blue Shirt", not "Blue Shirt delete button". SC 2.5.3 requires the visible text to be contained in the accessible name, and leading with it also makes Voice Control matching more forgiving.

Disabled and loading states
Keep disabled buttons visible to VoiceOver. Removing them from the tree means the user cannot tell the action exists. Announcing "dimmed" tells them it exists but is currently unavailable — and then they know to look for what unlocks it.
// SwiftUI — disabled
Button("Submit") { submit() }
    .disabled(!formIsValid)
// VoiceOver: "Submit, dimmed, button" — .notEnabled applied automatically

// SwiftUI — loading
Button(action: submitTapped) {
    if isLoading { ProgressView() } else { Text("Submit") }
}
.accessibilityLabel(isLoading ? "Submitting, please wait" : "Submit")
.disabled(isLoading)

// UIKit
submitButton.isEnabled = !isLoading
submitButton.accessibilityLabel = isLoading ? "Submitting, please wait" : "Submit"
Destructive actions 
Button("Delete Account") { showConfirm = true }
    .accessibilityLabel("Delete Account")
    .accessibilityHint("Permanently deletes your account. This cannot be undone.")
How to test
  1. With VoiceOver on, swipe to each button. Confirm it announces label then "button".
  2. Double tap to activate. If nothing happens, the control is a tap gesture rather than a real button.
  3. Open the rotor, select Buttons, and swipe down. Every action on screen should be listed and every entry should be distinguishable from the others.
  4. Turn on Voice Control (Settings → Accessibility → Voice Control). Say "Tap [visible label]" for each button. Then say "Show names" — every actionable control should get a name badge.
  5. Turn on Switch Control and run one full scan cycle. Any button the scanner skips is unreachable for motor-impaired users.
  6. Disable a button through the UI and confirm VoiceOver now says "dimmed" rather than the button disappearing.
Checkpoints
☐Every icon-only button has a descriptive label
☐No interactive element uses .onTapGesture in place of Button
☐Repeated buttons include item context in the label
☐Visible text appears at the start of the accessible label (SC 2.5.3)
☐Disabled buttons remain in the accessibility tree and announce "dimmed"
☐Loading state changes the label so the user knows work is in progress
☐Destructive actions carry a hint explaining the consequence
☐Every button is reachable by Switch Control scanning
Common failures
SF Symbol name read aloud: "square dot and dot arrow dot up" instead of "Share". Occurs on every icon button with no label.
onTapGesture instead of Button: the visual works, the accessibility does not. Fails 4.1.2 and 2.1.1 simultaneously.
Icon and text both announced: a button containing an icon plus "Share" text reads "share dot up, Share, button". Hide the decorative icon with .accessibilityHidden(true).
Label does not contain visible text: button shows "Send" but the label is "Submit message" — Voice Control users say "Tap Send" and nothing happens. Direct 2.5.3 failure.
Disabled buttons removed entirely: the control vanishes from the tree, so the user cannot discover the action exists at all.
WCAG mapping
4.1.2 A Name, Role, Value — button role and name must be exposed.
1.1.1 A Non-text Content — icon buttons require a text alternative.
2.5.3 A Label in Name — accessible name must contain the visible label.
2.1.1 A Keyboard — action must be operable without a pointing device.

05 — Images and icons

What it is: any non-text visual — photos, illustrations, SF Symbols, charts, avatars.
Why it matters: images fall into three categories and each needs opposite treatment. Getting the category wrong either strips information from the user or floods them with noise they have to swipe past.
CategoryExampleTreatment
InformativeProduct photo, chart, user avatarDescriptive accessibilityLabel
DecorativeBackground gradient, divider flourish, shadow.accessibilityHidden(true)
FunctionalIcon inside a button, tappable thumbnailLabel describes the action, not the picture
RedundantIcon sitting next to text that says the same thingHide the icon, let the text speak
 
// Informative
Image("goa_beach_villa")
    .accessibilityLabel("Beachfront villa in Goa with private pool and ocean view")

// Decorative — two equivalent ways
Image("card_shadow").accessibilityHidden(true)
Image(decorative: "background_gradient")

// Functional — describes the action
Image(systemName: "location.fill")
    .accessibilityLabel("View property on map")
    .accessibilityAddTraits(.isButton)

// Redundant — hide the icon
HStack(spacing: 6) {
    Image(systemName: "bed.double.fill").accessibilityHidden(true)
    Text("3 Bedrooms")
}
// VoiceOver: "3 Bedrooms" — clean ✓
UIKit equivalents 
photoView.isAccessibilityElement = true
photoView.accessibilityLabel = "Beachfront villa in Goa with private pool"

decorativeView.isAccessibilityElement = false   // hidden

iconButton.accessibilityLabel = "View property on map"
Charts and complex graphics

A chart's label should carry the finding, not a description of the shapes. "Bar chart" tells the user nothing. iOS 15+ also supports Audio Graphs, which let VoiceOver users hear the data as sound.

ChartView(data: revenue)
    .accessibilityLabel("Quarterly revenue by region")
    .accessibilityValue("Asia-Pacific leads at 4.2 million dollars, "
                      + "North America 3.8 million, Europe 2.1 million")
How to test
  1. With VoiceOver on, swipe through the screen and listen to every image announcement.
  2. Any image announcing a file name or SF Symbol name is missing its label.
  3. Any decorative image that VoiceOver stops on is noise — it should be skipped entirely.
  4. For each informative image, ask: if I could not see this, would the announcement give me the same information? If not, the label is too thin.
  5. Open the rotor and select Images. Review the list — it should contain only meaningful images.
  6. In Accessibility Inspector, confirm decorative images are absent from the tree rather than present with an empty label.
Checkpoints
☐Every informative image has a label that conveys its content
☐Decorative images are hidden, not given empty labels
☐Icons paired with visible text are hidden from VoiceOver
☐Functional icons describe the action, not the graphic
☐No label starts with "image of" or "picture of" — VoiceOver already says "image"
☐Charts convey the data trend, not just the chart type
Common failures
File name announced: "IMG underscore 4471 dot png" — the label was never set.
SF Symbol name announced: "chevron dot right" when the intent was "Open details".
Decorative images not hidden: a VoiceOver user swipes through six background shapes before reaching the content.
Duplicate announcement: icon and adjacent text both read, producing "person dot circle, Profile".
Chart labelled as "chart": no data conveyed at all — an information failure under 1.1.1.
WCAG mapping
1.1.1 A Non-text Content — all meaningful images need a text alternative.
1.4.5 AA Images of Text — avoid rendering text as an image where real text will do.

06 — Text fields

What it is: TextField, SecureField, TextEditor, and their UIKit counterparts.
Why it matters: forms are where users commit to something — signing up, paying, booking. A field whose label vanishes the moment you start typing leaves a VoiceOver user filling in a box they can no longer identify.
⚠️

A placeholder is not a label. It disappears on first keystroke, is often below contrast minimums, and cannot be re-read by a screen reader after the field has content. Always set an explicit accessibilityLabel — ideally alongside a visible label above the field.

Placeholder as the only label 
TextField("Email Address", text: $email)
// Once the user types, the label is gone from screen
// VoiceOver on a filled field: "sushil@example.com, text field"
// The user no longer knows what this field is for
SwiftUI 
VStack(alignment: .leading, spacing: 4) {
    Text("Email Address")            // visible, persistent
    TextField("", text: $email)
        .accessibilityLabel("Email Address")
        .accessibilityHint("Enter the email you registered with")
        .textContentType(.emailAddress)   // enables autofill
        .keyboardType(.emailAddress)
        .accessibilityInputLabels(["Email Address", "Email", "E-mail"])
}
UIKit 
emailField.accessibilityLabel = "Email Address"
emailField.accessibilityHint  = "Enter the email you registered with"
emailField.textContentType    = .emailAddress
emailField.keyboardType       = .emailAddress
emailField.accessibilityUserInputLabels = ["Email Address", "Email"]
textContentType is an accessibility feature, not just a convenience. It powers autofill, which removes the need to type at all — a significant benefit for users with motor or cognitive disabilities. It maps directly to the web's autocomplete attribute and WCAG SC 1.3.5.
Errors — announce and move focus

A red border communicates nothing to a VoiceOver user. The error needs to reach them through the accessibility layer and focus needs to land on the field that failed.

// SwiftUI
TextField("", text: $email)
    .accessibilityLabel("Email Address")
    .accessibilityValue(hasError ? "Error: \(errorMessage)" : email)

// UIKit — set the value, then move focus to the field
emailField.accessibilityValue = "Error: Please enter a valid email address"
UIAccessibility.post(notification: .layoutChanged, argument: emailField)
VoiceOver announces: "Email Address, Error: Please enter a valid email address, text field"
Secure fields 
SecureField("", text: $password)
    .accessibilityLabel("Password")
    .textContentType(.password)
// VoiceOver: "Password, secure text field"
// VoiceOver deliberately does not read back the characters
How to test
  1. With VoiceOver on, swipe to each field. Confirm it announces label, then any value, then "text field".
  2. Type something into a field, then swipe away and back. The label must still be announced — if only the typed text is read, the label was a placeholder.
  3. Submit the form with deliberate errors. Confirm focus moves to the first failed field and the error text is announced, not just shown.
  4. Open the rotor, select Form Controls, and confirm every field is listed with a distinct name.
  5. Turn on Voice Control and say "Tap [label]" for each field. Try the short natural form as well — "Tap Email" for "Email Address".
  6. Check autofill: tap a field and confirm the keyboard offers saved credentials where textContentType applies.
Checkpoints
☐Every field has a persistent label that survives typing
☐Placeholder is never the only source of the label
☐textContentType set on name, email, phone, address, and credential fields
☐Errors update accessibilityValue and are announced
☐Focus moves to the first field in error on failed submission
☐Required fields are indicated in the label or hint, not by colour alone
☐Keyboard type matches the expected input
☐Error text explains how to fix, not just that something is wrong
Common failures
Placeholder-only labelling: the most frequent form finding on iOS. Fails 3.3.2 and 4.1.2.
Silent validation: the field turns red, VoiceOver announces nothing, focus stays where it was. The user cannot tell submission failed.
Generic errors: "Invalid input" with no explanation of the expected format. Fails 3.3.3.
Missing textContentType: autofill unavailable, forcing manual typing of long strings — a real barrier for motor and cognitive disabilities.
Required marked by asterisk colour only: conveyed visually and never programmatically.
WCAG mapping
3.3.2 A Labels or Instructions — every input needs a label.
3.3.1 A Error Identification — errors identified and described in text.
3.3.3 AA Error Suggestion — tell the user how to correct it.
1.3.5 AA Identify Input Purpose — textContentType is the iOS equivalent of autocomplete.

07 — Toggles and switches

What it is: a binary on/off control that takes effect immediately — no Save button.
Why it matters: the entire value of a toggle is its current state. If VoiceOver announces "Notifications, switch" without saying whether it is on or off, the user has to flip it and observe the result to find out what it was.
SwiftUI — native, nothing extra required 
Toggle(isOn: $notificationsEnabled) {
    Text("Push Notifications")   // becomes the accessibility label
}
// Off: "Push Notifications, off, switch button"
// On:  "Push Notifications, on, switch button"
// Voice Control: "Tap Push Notifications" ✓
⚠️

UIKit does not link the label to the switch for you. A UILabel beside a UISwitch are two unrelated elements. VoiceOver reads the label, swipes to the switch, and announces just "off, switch button" with no idea what is off.

UIKit — link them manually 
notificationSwitch.accessibilityLabel = "Push Notifications"
// Optionally hide the separate visual label to avoid a double announcement:
notificationLabel.isAccessibilityElement = false
Custom toggles 
// SwiftUI — Button wrapper, never onTapGesture
Button(action: { isOn.toggle() }) {
    ZStack(alignment: isOn ? .trailing : .leading) {
        Capsule().fill(isOn ? Color.green : Color.gray)
        Circle().fill(.white).padding(2)
    }
    .frame(width: 52, height: 32)
}
.accessibilityLabel("Push Notifications")
.accessibilityValue(isOn ? "On" : "Off")
.accessibilityAddTraits(isOn ? .isSelected : [])

// UIKit
self.accessibilityLabel = "Push Notifications"
self.accessibilityValue = isOn ? "On" : "Off"
self.accessibilityTraits = .button
// Announce the change so the user gets confirmation
UIAccessibility.post(notification: .announcement,
                     argument: "Push Notifications \(isOn ? "on" : "off")")
How to test
  1. With VoiceOver on, swipe to the toggle. It must announce label, current state, and role — all three.
  2. Double tap to flip it. VoiceOver should announce the new state immediately.
  3. Swipe away and back. The announced state must match what is displayed.
  4. Turn off VoiceOver and check the visual: is the on/off difference conveyed by more than colour alone? Position of the knob counts; a green-versus-grey capsule with no other difference does not.
  5. Voice Control: say "Tap [label]" and confirm the toggle responds.
  6. Enable Settings → Accessibility → Display & Text Size → On/Off Labels and confirm the I/O indicators appear on system switches.
Checkpoints
☐Current state is announced on focus, not only after flipping
☐State change is announced when the user activates it
☐UIKit switches have accessibilityLabel set explicitly
☐State is not conveyed by colour alone visually
☐Custom toggles use Button, not .onTapGesture
☐Label describes what is being switched, not the switch itself
Common failures
State missing: "Notifications, switch button" with no on or off. The user must toggle it to discover the original state — and has now changed a setting they may not have wanted to change.
UIKit label not linked: "off, switch button" with no indication of what is off.
State baked into the label: accessibilityLabel = "Notifications On" — the name changes with state, so the control has no stable identity for Voice Control.
Colour-only state: green versus grey with the knob in the same position. Fails 1.4.1 for colour-blind users.
WCAG mapping
4.1.2 A Name, Role, Value — state is the "value" part.
1.4.1 A Use of Color — state must not rely on colour alone.

08 — Sliders

What it is: a control for selecting a value within a range — volume, brightness, price filters.
Why it matters: sliders are inherently gesture-based. A VoiceOver user cannot drag a thumb along a track; they rely on the adjustable trait, which converts swipe up and swipe down into increment and decrement. Without it the control is completely unusable.
SwiftUI — native slider 
Slider(value: $volume, in: 0...100, step: 1)
    .accessibilityLabel("Volume")
    .accessibilityValue("\(Int(volume)) percent")
// "Volume, 50 percent, adjustable"
// Swipe up → increases, swipe down → decreases — automatic ✓
⚠️

UIKit's UISlider does not update accessibilityValue on its own. Set it once at build time and VoiceOver will announce that stale number forever, no matter how the user adjusts it. This is a subtle bug that passes visual review and fails every screen reader test.

UIKit — update the value on change 
slider.minimumValue = 0
slider.maximumValue = 100
slider.accessibilityLabel = "Volume"
slider.accessibilityValue = "\(Int(slider.value)) percent"

slider.addTarget(self, action: #selector(sliderChanged), for: .valueChanged)

@objc func sliderChanged() {
    slider.accessibilityValue = "\(Int(slider.value)) percent"
}
Custom sliders — three approaches

A custom-drawn slider has no adjustable behaviour by default. You have three options, in order of preference.

1. accessibilityRepresentation — best. Hand VoiceOver a real Slider while the screen keeps your design.

CustomSliderShape(value: $budget)
    .accessibilityRepresentation {
        Slider(value: $budget, in: 0...5000, step: 100)
            .accessibilityLabel("Maximum budget")
            .accessibilityValue("\(Int(budget)) rupees")
    }
// Swipe up/down works with no adjustable action written ✓

2. accessibilityAdjustableAction — SwiftUI manual.

CustomSliderShape(value: $budget)
    .accessibilityLabel("Maximum budget")
    .accessibilityValue("\(Int(budget)) rupees")
    .accessibilityAdjustableAction { direction in
        switch direction {
        case .increment: budget = min(budget + 100, 5000)
        case .decrement: budget = max(budget - 100, 0)
        @unknown default: break
        }
    }

3. UIKit .adjustable trait plus overrides.

self.accessibilityTraits = .adjustable
self.accessibilityLabel  = "Maximum budget"
self.accessibilityValue  = "0 rupees"

override func accessibilityIncrement() {
    budget = min(budget + 100, 5000)
    accessibilityValue = "\(Int(budget)) rupees"
}

override func accessibilityDecrement() {
    budget = max(budget - 100, 0)
    accessibilityValue = "\(Int(budget)) rupees"
}
Choose a sensible step size. A 0–5000 range with a step of 1 requires 5000 swipes to cross. Steps should let a user reach any reasonable value in ten to twenty gestures.
How to test
  1. With VoiceOver on, focus the slider. It must announce label, current value, and "adjustable".
  2. Swipe up with one finger. The value must increase and the new value must be announced.
  3. Swipe down. The value must decrease and announce.
  4. Push to both extremes. Confirm it stops cleanly at minimum and maximum without wrapping or overflowing.
  5. Count the swipes needed to cross the full range. More than about twenty means the step is too small.
  6. Confirm the value has units — "50 percent" or "1200 rupees", not a bare "50".
  7. Enable Full Keyboard Access with a Bluetooth keyboard and confirm arrow keys adjust the value.
Checkpoints
☐Slider announces the adjustable trait
☐Swipe up and down change the value
☐Value updates and is announced after every adjustment
☐Value includes units, not a bare number
☐Step size makes the full range reachable in a reasonable number of gestures
☐Range boundaries are respected
☐UIKit sliders update accessibilityValue in the value-changed handler
Common failures
Stale UIKit value: announces the initial value forever because the update handler was never wired up.
Custom slider with no adjustable action: VoiceOver can focus it but not change it. Complete blocker.
Bare numbers: "Volume, 50" — fifty of what? Percent, decibels, steps?
Step too small: a price filter from 0 to 100,000 in steps of 1 is unusable by swipe.

4.1.2 A Name, Role, Value — the value must be current and exposed.
2.1.1 A Keyboard — value must be changeable without dragging.

09 — Alerts

What it is: a small modal interrupting the user with a message and one or two actions.
Why it matters: alerts appear without warning and demand a decision. If focus does not move into the alert, a VoiceOver user hears nothing change while the rest of the screen quietly becomes untappable.

// VoiceOver reads: title → message → buttons

Custom alerts — the three things you must add

  3. Perform the two-finger Z escape gesture. The alert should dismiss as if Cancel were tapped.
  4. Dismiss the alert normally and confirm focus returns to the control that opened it — not to the top of the screen.
  5. Confirm every alert button is reachable and correctly labelled.
  6. Repeat with Switch Control to verify the scanner stays inside the alert.

13 — Focus management

What it is: deliberately moving VoiceOver's cursor when the interface changes.
Why it matters: sighted users notice a change instantly through peripheral vision. VoiceOver users only know what is under the cursor. If the screen changes and focus does not move, the change effectively did not happen.
ScenarioNotificationTarget
Modal or new screen appears.screenChangedTitle, or nil for first element
Modal dismissed.screenChangedThe control that opened it
Validation error appears.layoutChangedThe field in error
Content inserted in place.layoutChangedThe new content, or nil

15 — Announcements and live updates

What it is: speaking a message to VoiceOver without moving focus — the iOS equivalent of an ARIA live region.
Why it matters: a toast saying "Saved" appears and disappears in three seconds. A sighted user catches it. A VoiceOver user, focused elsewhere, gets nothing unless you announce it explicitly. 
// SwiftUI, iOS 17+
AccessibilityNotification.Announcement("Item added to cart").post()

// SwiftUI, iOS 15/16 and UIKit — universal
UIAccessibility.post(notification: .announcement, argument: "Item added to cart")

// Announcement priority, iOS 17+
var announcement = AttributedString("Payment failed")
announcement.accessibilitySpeechAnnouncementPriority = .high
AccessibilityNotification.Announcement(announcement).post()
⚠️

Identical announcements are suppressed. Posting the same string twice in a row means the second one is silently dropped. For a repeating event like "3 results", vary the string or include a changing detail so the user actually hears each update.

Frequently updating values

A live timer or score that updates every second will flood VoiceOver with speech. The .updatesFrequently trait tells the system to sample the value rather than announce every change.

Text(timeRemaining)
    .accessibilityLabel("Time remaining")
    .accessibilityValue(timeRemaining)
    .accessibilityAddTraits(.updatesFrequently)

        // VoiceOver was turned on or off mid-session
}

  1. With VoiceOver on, trigger every toast, snackbar, and inline status message. Each must be spoken.

  3. Submit a form successfully and confirm the success state is announced, not just displayed.
  4. Trigger a background operation — sync, upload — and confirm both start and completion are announced.
  5. Watch any live-updating value for thirty seconds. Constant interruption means .updatesFrequently is missing.
  6. Confirm announcements do not steal focus. The cursor should stay where the user left it.

16 — Touch targets

What it is: the tappable area of a control, which is often larger or smaller than what is drawn.
Why it matters: a user with a tremor, limited dexterity, or a prosthetic cannot reliably hit a 16-point icon. Targets that are too small produce mis-taps, and on destructive controls a mis-tap has real consequences.
⚠️

Do not confuse the two numbers. WCAG 2.2 SC 2.5.8 (Level AA) requires 24×24 CSS pixels, or adequate spacing. Apple's Human Interface Guidelines recommend 44×44 points. The 44pt figure is a platform recommendation, not the AA compliance threshold. Reporting a 30pt target as a WCAG AA failure is a false positive.

// SwiftUI — expand the tap area without changing the visual
Button(action: close) {
    Image(systemName: "xmark")

// UIKit — enlarge the hit area on a small control
class LargeTapButton: UIButton {
    override func point(inside point: CGPoint, with event: UIEvent?) -> Bool {
        bounds.insetBy(dx: -10, dy: -10).contains(point)
    }
}
.contentShape(Rectangle()) matters. Without it, a frame around an icon expands the layout but the tappable region stays the size of the glyph. The control looks bigger and behaves the same.
How to test
  1. Open Accessibility Inspector, connect to the running app, and inspect each small control. The frame size is shown directly.
  2. Turn on Switch Control and scan the screen — undersized targets often reveal themselves as hard-to-select items.
  3. Tap each small control ten times with a thumb, not an index finger. Count the misses.
  4. Check spacing between adjacent controls. Two 24pt targets touching each other still cause mis-taps; SC 2.5.8 allows small targets only when spacing compensates.
  5. Pay special attention to close buttons, delete icons, and anything in a toolbar or nav bar — these are usually the smallest.
Checkpoints
☐All interactive targets meet at least 24×24pt (WCAG AA)
☐Primary and destructive actions meet 44×44pt (Apple HIG)
☐Adjacent targets have adequate spacing between them
☐.contentShape applied where the frame was expanded
☐Targets do not overlap
Common failures
Icon-sized close buttons: a 16pt X in the corner of a modal, frequently mis-tapped.
Frame without contentShape: the layout reserves 44pt but only the glyph responds to touch.
Crowded toolbars: five icons packed edge to edge with no spacing.
False positives in reports: flagging every sub-44pt target as a WCAG AA failure. The AA threshold is 24pt.
WCAG mapping
2.5.8 AA Target Size (Minimum) — 24×24 CSS pixels, or spacing equivalent. WCAG 2.2.
2.5.5 AAA Target Size (Enhanced) — 44×44. WCAG 2.1.

17 — Dynamic Type

What it is: the system text-size setting, which users can push up to roughly 310% of default through the accessibility sizes.
Why it matters: this is the single most widely used accessibility feature on iOS, and by a large margin — far more people enlarge text than run VoiceOver. A layout that breaks at large sizes affects a substantial share of real users.
Fixed size — ignores the user's setting 
// SwiftUI
Text("Account balance").font(.system(size: 15))

// UIKit
label.font = UIFont.systemFont(ofSize: 15)
Scales with the user's setting 
// SwiftUI — semantic text styles scale automatically
Text("Account balance").font(.subheadline)

// SwiftUI — custom font that still scales
Text("Balance").font(.custom("Inter", size: 15, relativeTo: .subheadline))

// UIKit — both lines are required
label.font = UIFont.preferredFont(forTextStyle: .body)
label.adjustsFontForContentSizeCategory = true
⚠️

In UIKit, preferredFont(forTextStyle:) alone is not enough. Without adjustsFontForContentSizeCategory = true, the label picks up the size at creation and never updates when the user changes the setting mid-session.

Layouts that survive large text 
// Switch a horizontal layout to vertical at accessibility sizes
@Environment(\.dynamicTypeSize) var typeSize

var body: some View {
    if typeSize.isAccessibilitySize {
        VStack(alignment: .leading) { icon; label; value }
    } else {
        HStack { icon; label; Spacer(); value }
    }
}

// Or use ViewThatFits to pick automatically
ViewThatFits {
    HStack { icon; label; Spacer(); value }
    VStack(alignment: .leading) { icon; label; value }
}
Never cap text scaling to protect a layout. .dynamicTypeSize(...DynamicTypeSize.large) limits how far a user can enlarge text. Fix the layout instead — capping the setting is choosing your design over your user's ability to read.
How to test
  1. Go to Settings → Accessibility → Display & Text Size → Larger Text, enable Larger Accessibility Sizes, and drag the slider to maximum (AX5).
  2. Walk every screen of the app. Text must grow — anything that stays the same size is using a fixed font.
  3. Look for truncation with an ellipsis where the full string matters, overlapping elements, and text clipped by a fixed-height container.
  4. Confirm no horizontal scrolling has been introduced.
  5. Check that buttons still show their full label rather than "Contin…".
  6. Change the setting while the app is running and confirm the UI updates live rather than requiring a relaunch.
  7. Test in landscape at maximum size as well — that combination breaks the most layouts.
Checkpoints
☐All text uses semantic text styles or relativeTo: custom fonts
☐UIKit labels set adjustsFontForContentSizeCategory = true
☐App is fully usable at AX5
☐No content is truncated or clipped at large sizes
☐No horizontal scrolling appears
☐Text size is not capped in code
☐Layout adapts — horizontal stacks reflow to vertical where needed
Common failures
Fixed point sizes: text does not scale at all. Fails 1.4.4.
Missing adjustsFontForContentSizeCategory: UIKit text scales on launch but not when the setting changes.
Clipped text: a fixed-height container cuts off the second line at large sizes.
Truncated buttons: "Continue to payment" becomes "Contin…".
Capped scaling: the app refuses to go beyond the default size, overriding an explicit user preference.
WCAG mapping
1.4.4 AA Resize Text — text must resize to 200% without loss of content or function.
1.4.10 AA Reflow — content must reflow without two-dimensional scrolling.

18 — Motion, contrast, and system settings

What it is: the system accessibility preferences an app is expected to respect — Reduce Motion, Increase Contrast, Reduce Transparency, Bold Text, Differentiate Without Colour.
Why it matters: the user has already told the system what they need. Ignoring those settings means the app overrides an explicit accessibility choice. For someone with vestibular disorder, an unskippable parallax animation can cause genuine nausea. 
// SwiftUI — read every relevant setting from the environment
@Environment(\.accessibilityReduceMotion)        var reduceMotion
@Environment(\.accessibilityReduceTransparency)  var reduceTransparency
@Environment(\.accessibilityDifferentiateWithoutColor) var differentiateWithoutColor
@Environment(\.legibilityWeight)                 var legibilityWeight   // Bold Text

var body: some View {
    CardView()
        .animation(reduceMotion ? nil : .spring(), value: isExpanded)
        .background(reduceTransparency ? Color(.systemBackground) : .ultraThinMaterial)
}

// UIKit
if UIAccessibility.isReduceMotionEnabled       { /* skip the animation */ }
if UIAccessibility.isReduceTransparencyEnabled { /* use a solid background */ }
if UIAccessibility.isBoldTextEnabled           { /* heavier weight */ }
if UIAccessibility.shouldDifferentiateWithoutColor { /* add shapes or labels */ }

ContentAAAAA
Body text under 18pt4.5:17:1
Large text 18pt+, or 14pt bold+3:14.5:1

Use semantic system colours. Color(.label), Color(.secondaryLabel), and Color(.systemBackground) adapt automatically to light mode, dark mode, and Increase Contrast. Hardcoded hex values do none of that.
How to test
  1. Enable Settings → Accessibility → Motion → Reduce Motion. Walk the app. Parallax, spring animations, and auto-playing transitions should be reduced to cross-fades or removed entirely.
  2. Enable Display & Text Size → Increase Contrast and confirm borders and text become more distinct rather than staying identical.
  3. Enable Reduce Transparency and confirm blurred backgrounds become solid and text over them stays readable.
  4. Enable Bold Text and confirm the app's text weight responds.
  5. Enable Differentiate Without Colour and check every status indicator — a red-versus-green dot with no shape or label difference is a failure.
  6. Measure contrast with the Colour Contrast Analyser on screenshots, in both light and dark mode. Dark mode is frequently worse and frequently untested.
  7. Enable Smart Invert and confirm images and logos are not inverted into unreadable negatives.
Checkpoints
☐Reduce Motion removes or replaces non-essential animation
☐No animation flashes more than three times per second
☐Auto-playing content can be paused
☐Text meets 4.5:1 in both light and dark mode
☐Icons and borders meet 3:1
☐Status is never conveyed by colour alone
☐Semantic system colours used rather than hardcoded values
☐Reduce Transparency produces readable solid backgrounds
Common failures
Reduce Motion ignored: full parallax and spring animations regardless of the setting. A vestibular trigger.
Dark mode contrast untested: light mode passes, dark mode drops to 3:1 on body text.
Colour-only status: a red dot for offline and green for online with no shape, icon, or text difference. Fails 1.4.1.
Hardcoded colours: fixed hex values that ignore Increase Contrast entirely.
Text over a blur: readable with transparency on, illegible when Reduce Transparency changes the background.
WCAG mapping
1.4.3 AA Contrast (Minimum) — 4.5:1 for body text, 3:1 for large text.
1.4.11 AA Non-text Contrast — 3:1 for UI components and graphics.
1.4.1 A Use of Color — colour must not be the sole carrier of information.
2.3.3 AAA Animation from Interactions — motion animation must be disableable.
2.2.2 A Pause, Stop, Hide — auto-playing motion needs a control.

Audit workflow

A repeatable order of operations, roughly fastest-to-slowest, so cheap findings surface before you spend time on deep manual testing.

  1. Accessibility Inspector audit. Xcode → Open Developer Tool → Accessibility Inspector, target the running app, run the automated audit per screen. Catches missing labels, small hit areas, and contrast issues in seconds. Treat it as a starting point, not a report.
  2. Dynamic Type at AX5. Set text to maximum and walk every screen. Layout breaks show up immediately and affect the largest user group.
  3. VoiceOver reading order. Two-finger swipe down on each screen. Confirm announcement order matches visual order.
  4. VoiceOver element-by-element. Swipe right through every screen. Check label, role, value, and state on each control.
  5. Rotor check. Headings, Links, Form Controls, and Actions on each screen. Empty rotors are findings.
  6. Interaction test. Double tap every button, adjust every slider, flip every toggle. Confirm each one responds and announces the change.
  7. Focus management. Open and dismiss every modal. Submit every form with errors. Confirm focus lands correctly each time.
  8. Voice Control. Turn it on, say "Show names", and verify every control has a name that matches its visible label.
  9. Switch Control. Run one scan cycle per screen. Anything the scanner skips is unreachable.
  10. System settings. Reduce Motion, Increase Contrast, Reduce Transparency, Bold Text, Differentiate Without Colour — one pass each.
  11. Contrast measurement. Colour Contrast Analyser on screenshots in both light and dark mode.
  12. Screen curtain run. Three-finger triple tap, then complete one full user journey without seeing the screen. This is where usability problems that pass every criterion still reveal themselves.
✓

Automated tooling catches roughly 30% of real issues on native iOS — and the Accessibility Inspector's audit is narrower than that. Missing labels it will find. A button that announces correctly but does nothing when double-tapped, it will not. Manual testing is the audit; automation is triage.

The pattern behind almost every finding

Reading back through eighteen components, the failures rhyme. Almost all of them come from one of four places.

A custom view replaced a native control. onTapGesture instead of Button, a drawn capsule instead of Toggle, a custom track instead of Slider. The visual is identical and the accessibility is gone.
State was never exposed. The toggle knows it is on, the tab knows it is selected, the slider knows its value — and none of that reaches the accessibility layer.
Something changed and nobody was told. A modal opened, a form failed, a toast appeared. Focus did not move and nothing was announced.
An icon had no words. SF Symbol names read aloud, file names announced, actions with no label at all.

The corresponding rule is short enough to remember: use the native control, expose the state, move the focus, name the icon. Most of an audit is checking those four things eighteen different ways.

The Accessibility Inspector will tell you a label is missing. It will not tell you that the label says "Submit" while the button says "Send", or that a VoiceOver user can reach a button they are not allowed to press. That gap is the job.
