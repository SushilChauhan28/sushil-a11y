01 · Getting startedIntroduction

What is an accessible form?

An accessible form is one that all users — whatever their abilities or the assistive technology they use — can perceive, understand, navigate, complete and submit. That goes well beyond adding labels: it covers semantic markup, keyboard operation, error handling, screen reader support, cognitive load and the WCAG success criteria that apply to user input.

In practice, accessible forms use native HTML elements, explicit label associations, ARIA only where HTML falls short, specific error messages, a logical tab order and sufficient contrast. They are verified with keyboard-only testing, screen readers and automated tools.

Why forms matter

Login, registration, checkout, search, feedback and settings all depend on forms. When a form is inaccessible, the service behind it is inaccessible. The WebAIM Million report consistently finds missing form labels among the most common failures on home pages.

The cost is not limited to disabled users. Accessible forms are more usable for everyone: higher completion rates, fewer support requests and lower legal risk. Inaccessible ones lead to abandoned checkouts, complaints and reputational damage.

Why inaccessible forms fail

They are built for one audience: a sighted person using a mouse. The typical failures follow from that — visual-only cues (colour, position, unlabelled icons), placeholder text as the only label, generic "Invalid input" messages, auto-advancing fields, and labels that are not programmatically associated. These are not edge cases. They stop real people finishing real tasks every day.

Who benefits?

🧑‍🦯Blind users

Depend on labels, ARIA and announced errors to understand and complete a form without visual information.

⌨️Keyboard users

Use Tab, arrow keys, Enter, Space and Escape to reach and operate every control in a logical order.

🔍Low vision users

Need sufficient contrast, resizable text, reflow and indicators that do not rely on colour alone.

🦾Motor disabilities

Need large targets, generous spacing and no interactions that demand precise pointer movement.

🧠Cognitive disabilities

Benefit from clear labels, plain language, predictable behaviour, autofill and generous time limits.

🎤Speech input users

Need visible labels that match the accessible name, so "click Submit" activates the Submit button.

📱Mobile users

Get the right on-screen keyboard from the right input type, and labels that stay visible while typing.

👴Older users

Age-related changes in vision, dexterity and memory mean accessible forms serve a growing share of users.

🌍Everyone

Clear labels, good errors, logical order and responsive layout improve the experience for every user.

    03 · Getting startedChoosing the right control

    Most form accessibility is decided the moment you pick an element. Native controls come with keyboard support, focus handling, a role and state for free; a styled <div> comes with none of it. Every control in the demo above follows this table.

    Focus management in forms

    • Failed submit: move focus to the error summary. Each summary link moves focus to its field.
    • Successful submit: leave focus where it is and announce the result in a status message, or navigate to a confirmation page with a clear heading.
    • Revealed fields: when a choice reveals follow-up questions, do not move focus; put them straight after the control that revealed them.
    • Dialogs: move focus into the dialog on open, keep it there, and return it to the control that opened it on close.
    • Never auto-advance focus when a field is "full" (e.g. after the 4th digit of a PIN) — it breaks corrections and surprises keyboard and screen reader users (3.2.2).

    04 · Core conceptsLabels

    Every form control needs a programmatically associated label. It tells users what to enter, gives the screen reader something to announce, and — for checkboxes and radios — makes the text a larger click target. Without one, assistive technology users are guessing.

    📏

    WCAG: 1.3.1 Info and Relationships, 2.4.6 Headings and Labels, 3.3.2 Labels or Instructions, 4.1.2 Name, Role, Value, and 2.5.3 Label in Name. Missing labels are among the most common failures in automated audits.

    Explicit labels (for / id)

    A <label> whose for matches the input's id is the gold standard. Clicking the label focuses the input, and screen readers announce the label when the input receives focus. It works for every input type in every browser and assistive technology.

    <label for="firstname">First name</label>
<input type="text" id="firstname" name="firstname" autocomplete="given-name">

    Implicit labels (wrapping)

    Wrapping the input inside the label also creates an association, and it is the natural choice for checkboxes and radios. Some older assistive technology and voice control software handled it less reliably, so for text fields prefer for/id — or use both.

    <label><input type="checkbox" name="terms"> I agree to the terms</label>

    aria-labelledby

    Use it when the label text already exists elsewhere — a heading, or several pieces of text combined. The value is a space-separated list of IDs, concatenated in order, and it overrides any <label>.

    <h3 id="contact-heading">Contact information</h3>
<!-- Name = "Contact information Your work email address" -->
<input type="email" id="email" aria-labelledby="contact-heading email-label">
<span id="email-label">Your work email address</span>

    aria-label

    aria-label gives an invisible name. It is a last resort for when no visible text can serve — a search field next to a magnifier button, for example. Overusing it splits the experience: sighted users see one thing, screen reader users hear another, and speech input users cannot say a name they cannot see.

    ⚠️

    When not to use aria-label: when visible text could be the label; to repeat visible text; or when a <label for> would work. If the information matters, make it visible.

    ✓ Accessible — visible label with for / id

    <label for="email">Email address</label>
<input type="email" id="email" name="email"
  autocomplete="email" required
  aria-describedby="email-help">
<span id="email-help">We will never share your email</span>

    Screen reader: "Email address, edit, required, We will never share your email"

    ✗ Inaccessible — placeholder as the only label

    <input type="email" name="email"
  placeholder="Enter your email">
<!-- No visible label once typing starts -->
<!-- No programmatic label -->

    Screen reader: often just "edit, blank" — the placeholder is an unreliable fallback name and disappears visually as soon as the user types.

    🧪

    QA tip: In Chrome DevTools, open Elements → Accessibility and check every input's computed Name. "(no name)" means the label is missing or broken. In NVDA, Insert+F7 opens the Elements List, which can be filtered to form fields.

    05 · Core conceptsGrouping

    Related controls belong in a <fieldset> with a <legend>. The legend is the question; the labels are the answers. Without it, a screen reader user hears "Email, radio button" with no idea what the options are for.

    📏

    WCAG: 1.3.1 Info and Relationships requires groups and relationships to be available programmatically. A radio group without a fieldset and legend (or an equivalent role="radiogroup" with a name) fails it.

    Radio group: with and without a fieldset

    ✗ Inaccessible — no grouping

    Contact preference

    Checkbox group

    Interests (select all that apply) 
    <fieldset>
  <legend>Interests (select all that apply)</legend>
  <label><input type="checkbox" name="interest" value="a11y"> Accessibility</label>
  <label><input type="checkbox" name="interest" value="ux"> UX design</label>
  <!-- fieldset + legend already expose the group and its name: no role or aria-label needed -->
</fieldset>

    Nested groups

    Fieldsets can nest to express a hierarchy. Most desktop screen readers announce each level, though support varies and some flatten deep nesting — two levels is a sensible maximum.

    <fieldset>
  <legend>Shipping address</legend>
  <label for="ship-street">Street</label>
  <input type="text" id="ship-street" autocomplete="shipping street-address">

  <fieldset>
    <legend>City and region</legend>
    <label for="ship-city">City</label>
    <input type="text" id="ship-city" autocomplete="shipping address-level2">
    <label for="ship-state">State</label>
    <input type="text" id="ship-state" autocomplete="shipping address-level1">
  </fieldset>
</fieldset>
    💡

    Developer note: Always use <fieldset>/<legend> for radios and related checkboxes. For other groupings where a fieldset is awkward, role="group" with aria-labelledby is the alternative. Do not add role="radiogroup" to a fieldset that already has a legend.

    06 · Core conceptsInstructions

    Instructions say how to fill in a field. They are different from labels (what the field is) and errors (what went wrong). Put them before or next to the field, associate them with aria-describedby, and keep them short.

    📏

    WCAG: 3.3.2 Labels or Instructions (Level A) requires instructions when content needs user input. Missing format rules for passwords, dates or file uploads is a Level A failure.

    Required fields

    State "Fields marked with * are required" before the first field. Native required already exposes the state, so you do not need aria-required as well — keep that for custom widgets.

    Password rules

    Be specific: "At least 8 characters". Associate the rules with aria-describedby and consider a strength indicator with a text value.

    Date format

    "03/04/2026" means different days in different locales. State the expected format, or use separate day, month and year fields.

    Phone format

    Give an example: "+1 555 123 4567". type="tel" brings up the phone keypad on mobile. Accept spaces, brackets and dashes rather than rejecting them.

    File uploads

    State accepted formats and the size limit ("PDF, DOC or DOCX, up to 5 MB"). The accept attribute filters the file dialog but does not replace the instruction.

    Character limits

    Show the count and maximum. Announce it through a polite live region only near the limit — announcing every keystroke talks over the user.

    Where should instructions appear?

    Before the input, between label and field, so they are seen before typing starts and are not hidden by browser autofill menus. Associate them with aria-describedby so screen readers announce them on focus. Form-wide instructions go at the top of the form.

    <label for="password">Password <span aria-hidden="true">*</span></label>
<span id="pw-rules">At least 8 characters.</span>
<input type="password" id="password" name="password" required
  autocomplete="new-password" aria-describedby="pw-rules">
    🔊

    Screen reader behaviour: NVDA announces something like "Password, protected, edit, required, At least 8 characters." The description follows the name, role and state, so the user has the full context before typing.

    07 · Core conceptsValidation

    Accessible validation gives clear, specific and actionable feedback that every user can perceive. Timing matters: validate the whole form on submit, and a single field on blur only once the user has typed in it — errors that fire as someone simply Tabs past a field are noise.

    📏

    WCAG: 3.3.1 Error Identification (A), 3.3.3 Error Suggestion (AA), and 3.3.4 Error Prevention (AA) for legal, financial or data-changing submissions.

    Types of validation

    Required

    Native required is announced on focus. The message names the field: "Enter your first name", not "Required".

    Email format

    type="email" helps, but validate on the server too. "Enter an email address in the correct format, like name@example.com".

    Password strength

    A strength bar needs a text equivalent. Announce level changes politely, not every keystroke.

    Length

    minlength / maxlength set the limits; show the count and describe it for screen readers.

    Pattern

    For phone numbers, postcodes or IDs, always explain the expected format in words — a regex is not an instruction.

    Mismatch

    Confirm-password needs JavaScript. Say exactly what is wrong: "Passwords do not match".

    Live validation demo

    The accessible form demo shows required-field checks, email and phone format checks, a password strength meter, password matching and a form-level error summary.

    ✓ Accessible — specific, associated error

    !Error: Enter an email address in the correct format, like jane@company.com

    ✗ Inaccessible — generic, unassociated error

    Error

    🧪

    QA: (1) Tab through without typing, then submit. (2) Enter invalid data in each field. (3) Listen with NVDA for the error summary. (4) Check focus moves to the summary on failure. (5) Check each error is referenced by its field's aria-describedby.

    08 · Core conceptsError handling

    A red border is not error handling. Errors must be identified in text, descriptive, associated with their field and announced to screen reader users. Never communicate an error through colour or an icon alone.

    ARIA for errors

    aria-invalid="true"

    Set on the field while it has an error; remove it once fixed. Screen readers add "invalid entry".

    aria-describedby

    Points at the error message so it is read with the field on focus. The most widely supported association.

    aria-errormessage

    Points at the error, but is only exposed when aria-invalid="true" is also set. Support is still less consistent than aria-describedby.

    role="alert"

    An assertive live region: interrupts current speech. Reserve it for one form-level message, not every field.

    role="status"

    A polite live region, read after current speech. Right for "Saved" or "3 results".

    aria-live="assertive"

    Interrupts immediately. Use sparingly — overuse makes a form exhausting to complete.

    Client-side and server-side validation

    Client-side

    Immediate feedback without a round trip. Associate each error with aria-invalid + aria-describedby and let one error summary provide the announcement, rather than firing role="alert" on every field.

    Server-side

    Always needed — client checks can be bypassed. Re-render the form with messages in place, aria-invalid set, values preserved, and focus on the error summary. Prefix the page title with "Error:".

    Error summary pattern

    When submission fails, show a summary above the form listing every error as a link to its field, and move focus to it. Focus is what gets it announced. The GOV.UK pattern also wraps the content in role="alert" as a safety net; do not add aria-live on top.

    <div id="error-summary" tabindex="-1">
  <div role="alert">
    <h2>There is a problem</h2>
    <ul>
      <li><a href="#firstname">Enter your first name</a></li>
      <li><a href="#email">Enter an email address in the correct format</a></li>
    </ul>
  </div>
</div>

<script>
  // after a failed submit
  document.getElementById('error-summary').focus();
</script>
    ⚠️

    Common mistake: using alert(). It steals focus, is not tied to any field, cannot be styled, and disappears before the user reaches the field they need to fix.

    09 · Core conceptsAutocomplete

    The autocomplete attribute tells the browser what data a field expects, so it can fill it from saved details and password managers. Every keystroke saved matters for people with motor impairments; not having to recall details matters for people with memory or cognitive impairments; and everyone finishes faster.

    📏

    WCAG: 1.3.5 Identify Input Purpose (AA) requires the purpose of fields collecting information about the user to be programmatically determinable. autocomplete is how you meet it. 3.3.7 Redundant Entry (A, new in 2.2) also benefits: autofill avoids re-typing.

    10 · Keyboard & screen readersKeyboard accessibility

    Every control must be operable with a keyboard alone. Screen reader users, switch users, many people with motor impairments and plenty of power users never touch a mouse. This is Level A — not optional.

    📏

    WCAG: 2.1.1 Keyboard (A), 2.1.2 No Keyboard Trap (A), 2.4.3 Focus Order (A), 2.4.7 Focus Visible (AA) and 2.4.11 Focus Not Obscured (Minimum) (AA, new in 2.2).

    Essential keyboard interactions

    Keyboard interactions in forms
    KeyActionWhere
    TabNext focusable elementEverywhere, in DOM order
    Shift+TabPrevious focusable elementEverywhere
    SpaceToggle / activateCheckboxes, switches, buttons, radios
    EnterActivate / submitButtons, links, implicit form submission from a text field
    Arrow keysMove and select within a groupRadio groups, selects, listboxes, menus
    EscapeDismissDialogs, popups, date pickers, autocomplete lists
    Home / EndFirst / lastText fields (caret), listboxes, sliders

    Focus indicator

    Every focusable element needs a visible focus indicator. If you remove the browser default, you must provide a clearly visible replacement — that is all 2.4.7 Focus Visible (AA) requires. The measurable targets (3:1 contrast against the unfocused state and an area at least a 2px perimeter) belong to 2.4.13 Focus Appearance (AAA), and are good practice to follow.

    ✓ Accessible — clear focus ring

    3px indigo outline with a 2px offset, like every control on this page.

    ✗ Inaccessible — no focus indicator

    Deliberate 2.4.7 failure: outline: none with no replacement. Only the text caret shows where you are.

    Logical tab order

    Tab order should follow the visual reading order. Never use a positive tabindex to reorder — fix the DOM instead, and do not let CSS (grid order, flex row-reverse, absolute positioning) move things away from their source position.

    ⚠️

    Keyboard traps: a user can Tab into a component but not out. Common causes: custom dropdowns that capture Tab, modals that never release focus, and keydown handlers that call preventDefault() on Tab. Test by Tabbing through the entire form and out the other side.

    11 · Keyboard & screen readersScreen reader behaviour

    Screen readers turn the accessibility tree into speech or braille. What they say depends on the screen reader, browser, platform and verbosity settings, but it follows the accessible name and description computation defined alongside WAI-ARIA.

    What gets announced

    When a control receives focus, screen readers typically announce the accessible name (label), the role (edit, combo box, radio button), the states (required, checked, invalid) and the description (help or error text via aria-describedby). The order varies.

    ⚠️

    These announcements are illustrative. Exact wording depends on the screen reader, browser and verbosity. VoiceOver says "edit text" where NVDA says "edit"; JAWS may drop "required" at low verbosity. Always verify on real assistive technology.

    NVDA

    Free and open source, for Windows; works best with Firefox and Chrome. Insert+F7 opens the Elements List (links, headings, landmarks, form fields). NVDA switches to focus mode automatically when a form field receives focus and back to browse mode with Escape. It has no separate forms dialog — that is JAWS (Insert+F5).

    JAWS

    Commercial, for Windows, with very thorough forms support. Insert+F5 lists form fields. Its verbose defaults add hints such as "type in text" and "to change the selection use the arrow keys".

    VoiceOver

    Built into macOS and iOS. Cmd+F5 toggles it on the Mac; the Rotor (Ctrl+Option+U) lists form controls. On iOS it is the primary assistive technology for millions of people.

    TalkBack

    Android's built-in screen reader, driven by swipe gestures. Test on a real device: mobile keyboards, zoom and touch targets all behave differently from desktop emulation.

    🧪

    No screen reader to hand? DevTools → Elements → Accessibility shows the computed Name, Role and Description of any element — the same data a screen reader reads. The inspector on this page shows a simplified version live.

    role="switch"On/off semanticsA checkbox that looks and acts like a switch<input type="checkbox" role="switch">
    ⚠️

    First rule of ARIA: if a native element or attribute gives you the semantics you need, use it. <label for> beats aria-label; <fieldset>/<legend> beats role="group"; required beats aria-required.

    14 · ReferenceCommon accessibility mistakes

    The failures that turn up most often in WebAIM data and real audits. Each shows the problem, its impact and the fix — use it as a debugging guide when reviewing a form.

    Problem: no <label> associated with the input.

    Impact: the screen reader says "edit, blank" — the user cannot know what to enter. Fails 1.3.1, 3.3.2 and 4.1.2.

    <label for="name">Name</label>
<input type="text" id="name" autocomplete="name">

    Problem: placeholder text used instead of a visible label.

    Impact: it vanishes on typing (a memory burden), is an unreliable accessible name, and is usually low contrast.

    <label for="name">Full name</label>
<input type="text" id="name" autocomplete="name">

    Problem: radios or related checkboxes not grouped.

    Impact: each option is announced without the question it answers. Fails 1.3.1.

    <fieldset>
  <legend>Payment method</legend>
  <label><input type="radio" name="pm" value="card"> Card</label>
  <label><input type="radio" name="pm" value="paypal"> PayPal</label>
</fieldset>

    Problem: password, date or file fields with no guidance.

    Impact: users have to guess the rules and fail repeatedly. Fails 3.3.2.

    <span id="pw-help">At least 8 characters</span>
<input type="password" aria-describedby="pw-help">

    Problem: Tab order does not match the visual layout.

    Impact: disorienting for keyboard and screen magnifier users. Usually caused by CSS reordering. Fails 2.4.3.

    Fix: make the DOM order match the visual order. Never use tabindex greater than 0.

    Problem: errors shown only by a red border or red text.

    Impact: invisible to many colour-blind users and to everyone using forced colours. Fails 1.4.1 and 3.3.1.

    Fix: pair colour with a text message, an icon, a thicker border, aria-invalid and aria-describedby.

    Problem: "Invalid input" or "Error" with no specifics.

    Impact: the user cannot work out what is wrong or how to fix it. Fails 3.3.1 and 3.3.3.

    Fix: say what happened and what to do: "Enter an email address in the correct format, like name@example.com".

    Problem: choosing an option silently changes other fields, e.g. the city list updates when a country is chosen.

    Impact: screen reader users do not know anything changed. Fails 4.1.3 Status Messages.

    Fix: announce it through a polite live region: "City options updated for Canada".

    Problem: the session expires mid-form without notice.

    Impact: people who need more time lose their work. Fails 2.2.1 Timing Adjustable.

    Fix: warn at least 20 seconds before expiry and let the user extend with a simple action (up to at least ten times).

    Problem: no autocomplete on fields about the user.

    Impact: no reliable autofill; everyone types everything. Fails 1.3.5 (AA).

    Fix: autocomplete="given-name", autocomplete="email" and so on.

    Problem: pale labels, hints, placeholders or input borders.

    Impact: low vision users cannot read the text or find the field. Text needs 4.5:1 (1.4.3); input borders and focus indicators need 3:1 (1.4.11).

    Fix: check every pair with a contrast analyser, including the input border against the page background.

    Problem: checkboxes, radios or buttons smaller than 24 × 24 CSS pixels with no spacing.

    Impact: hard to hit for people with tremors or limited dexterity. Fails 2.5.8 Target Size (Minimum) (AA, new in 2.2).

    Fix: make the whole label clickable and pad targets to at least 24 × 24 px (44 × 44 is better).

    Problem: submit stays disabled until every field is valid.

    Impact: users cannot find out what is blocking them; disabled buttons are skipped by Tab and often low contrast.

    Fix: keep submit enabled and show errors when it is pressed. If a disabled look is unavoidable, use aria-disabled="true" (not disabled) so it stays focusable, and block activation in script.

    Problem: a red asterisk (or red label) is the only indication, with no explanation.

    Impact: colour-blind users miss it, and nobody is told what the asterisk means.

    Fix: explain the asterisk at the start of the form, hide the symbol from screen readers, and use native required so "required" is announced.

    Problem: onpaste="return false" on password or code fields, or autocomplete="off" to defeat password managers.

    Impact: forces people to memorise and transcribe credentials — a cognitive function test. Fails 3.3.8 Accessible Authentication (Minimum) (AA, new in 2.2).

    Fix: allow paste, use autocomplete="current-password" / new-password / one-time-code.

    15 · ReferenceDeveloper checklist

    Use during code review and before merging any form change. Every item has a concrete do and don't.

    1. Visible label for every control

      Every input, select and textarea has a visible <label>.

      Do: <label for="email">Email</label>

      Don't: <input placeholder="Email"> with no label

    2. Programmatic label association

      for matches the input's id, or aria-labelledby references IDs that exist.

      Do: for="fname" + id="fname"

      Don't: for="name" + id="username"

    3. Required fields marked programmatically

      Native required plus a visible, explained indicator.

      Do: <input required> + "Fields marked with * are required"

      Don't: a red border as the only indication

    4. Help text via aria-describedby

      Formats, constraints and examples are associated with the input.

      Do: aria-describedby="help1" + <span id="help1">DD/MM/YYYY</span>

      Don't: help text that exists visually but is not associated

    5. Radio and checkbox groups use fieldset

      Related options are wrapped in <fieldset> with a <legend>.

      Do: <fieldset><legend>Size</legend>…</fieldset>

      Don't: a heading or paragraph as a visual-only group title

    6. Errors are descriptive and associated

      Messages say what is wrong and how to fix it, linked with aria-describedby.

      Do: "Enter an email address in the correct format" + aria-describedby="email-error"

      Don't: "Invalid" with no association

    7. aria-invalid set dynamically

      aria-invalid="true" when validation fails; removed when corrected.

      Do: input.setAttribute('aria-invalid', 'true') on error, removeAttribute on fix

      Don't: never set, or hard-coded "true" in the markup

    8. Error summary on failed submit

      Lists every error, each linking to its field; receives focus.

      Do: tabindex="-1" container, links to field IDs, .focus() after submit

      Don't: alert("Please fix the errors")

    9. Correct type and autocomplete

      Each field has the right type and autocomplete token.

      Do: type="email" autocomplete="email"

      Don't: type="text" autocomplete="off" on an email field

    10. Keyboard operable

      Every control reachable with Tab and operable with Enter / Space / arrows; no traps.

      Do: native controls, or custom widgets built to the APG pattern

      Don't: <div tabindex="0" onclick> with no key handling

    11. Visible focus indicator

      A focus ring with at least 3:1 contrast on every background.

      Do: :focus-visible { outline: 3px solid; outline-offset: 2px; }

      Don't: * { outline: none; } with no replacement

    12. Sufficient contrast

      Labels, hints and errors reach 4.5:1; input borders reach 3:1.

      Do: #1a1a1a on #faf9f6 (over 16:1), borders #52606f on white (6.3:1)

      Don't: light grey hints and #ddd input borders on white

    16 · ReferenceQA accessibility testing

    No single tool catches everything. Thorough coverage combines automated scans, keyboard testing, screen reader testing and visual inspection.

    1. Keyboard testing

    1. Start before the form, then Tab into it.

    2. Tab through every field and confirm the order matches the visual layout.

    3. Confirm every control shows a clearly visible focus indicator.

    4. Press Space on checkboxes and switches — they toggle.

    5. Use arrow keys in radio groups — selection moves within the group.

    6. Press Escape in any popup or date picker — it closes and focus returns.

    7. Submit with Enter and confirm focus goes to the error summary or a clear result.

    8. Tab past the last control and out of the form — no traps.

    2. Screen reader testing (NVDA)

    1. Open the page in Chrome or Firefox with NVDA running.

    2. Open the Elements List (Insert+F7), filter to form fields, and check every field has a sensible name.

    3. Tab to each field and listen for label, role, state and description.

    4. Confirm "required" is announced on required fields.

    5. Submit with errors and confirm the summary is announced.

    6. Follow a summary link and confirm focus lands in the field with its error read out.

    7. Fix the error and confirm "invalid entry" is no longer announced.

    8. In a radio group, confirm the group name and position ("2 of 3") are announced.

    3. Visual inspection

    1. Every label is visible and next to its field.

    2. Required indicators are present and explained.

    3. Errors are shown in text, not just colour or an icon.

    4. Complex fields (password, date, phone, file) have help text.

    5. All text meets 4.5:1 and input borders 3:1.

    6. At 400% zoom (320 CSS px) the form reflows with no horizontal scrolling.

    7. On a phone, labels stay visible, targets are easy to hit and the right keyboards appear.

    Testing tools

    Browser DevTools

    Elements → Accessibility shows the computed Name, Role and Description of anything. Built in, free, always available.

    axe DevTools

    Deque's extension and the engine behind many CI checks. Deque reports it finds around 57% of issues by volume.

    WAVE

    WebAIM's extension overlays errors, alerts and structure on the page. Good for a fast visual overview.

    17 · ReferenceWCAG mapping

    The WCAG 2.2 success criteria that matter most for forms, in plain language. Use it in design reviews, code reviews and test planning.

    WCAG 2.2 success criteria relevant to forms
    CriterionLevelWhat it means for forms
    1.3.1 Info and RelationshipsALabels are associated, groups use fieldset/legend, sections use headings. Structure seen is structure exposed.
    1.3.5 Identify Input PurposeAAFields collecting information about the user carry the right autocomplete token.
    1.4.1 Use of ColorAErrors, required fields and selected states are not shown by colour alone.
    1.4.3 Contrast (Minimum)AALabels, hints, errors and entered text reach 4.5:1 (3:1 for large text).
    1.4.11 Non-text ContrastAAInput borders, checkbox outlines and focus indicators reach 3:1 against adjacent colours.
    2.1.1 KeyboardAEvery control, including custom widgets, date pickers and file uploads, works from the keyboard.
    2.1.2 No Keyboard TrapAFocus can always leave a component with standard keys.
    2.2.1 Timing AdjustableASession time-outs can be turned off, adjusted or extended, with warning.
    2.4.3 Focus OrderATab order follows a meaningful sequence; no positive tabindex.
    2.4.6 Headings and LabelsAALabels and section headings describe their purpose ("Company name", not "Name").
    2.4.7 Focus VisibleAAEvery focusable control shows a visible focus indicator.
    2.4.11 Focus Not Obscured (Minimum) — new in 2.2AAA focused field is never entirely hidden by sticky headers, cookie banners or chat widgets.
    2.5.3 Label in NameAThe accessible name contains the visible label, so speech users can say what they see.
    2.5.8 Target Size (Minimum) — new in 2.2AATargets are at least 24 × 24 CSS px, or spaced so a 24 px circle around each does not overlap another.
    3.2.2 On InputAChanging a value does not submit, navigate or move focus unless the user was told first.
    3.3.1 Error IdentificationAErrors are identified in text and the field in error is identified.
    3.3.2 Labels or InstructionsALabels, required indicators and format instructions are provided.
    3.3.3 Error SuggestionAAErrors suggest a fix: "Enter a date in the past", not "Invalid date".
    3.3.4 Error Prevention (Legal, Financial, Data)AAImportant submissions are reversible, checked, or confirmed after a review step.
    3.3.7 Redundant Entry — new in 2.2AInformation already given in the same process is auto-filled or selectable ("Same as billing address").
    3.3.8 Accessible Authentication (Minimum) — new in 2.2AANo memorising or transcribing to log in: allow paste and password managers, or offer another method.
    4.1.2 Name, Role, ValueAEvery control exposes a name, role and current state/value; custom widgets do it through ARIA.
    4.1.3 Status MessagesAA"Saved", result counts and similar updates are announced without moving focus.

<script>
function validate(form) {
  const email   = form.querySelector('#v-email');
  const errorEl = form.querySelector('#v-email-error');
  const summary = document.getElementById('error-summary');
  const errors  = [];

  const ok = /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email.value.trim());
  if (!ok) {
    const msg = 'Enter an email address in the correct format, like name@company.com';
    errorEl.textContent = 'Error: ' + msg;
    errorEl.hidden = false;
    email.setAttribute('aria-invalid', 'true');
    email.setAttribute('aria-describedby', 'v-email-help v-email-error');
    errors.push({ id: 'v-email', msg });
  } else {
    errorEl.hidden = true;
    email.removeAttribute('aria-invalid');
    email.setAttribute('aria-describedby', 'v-email-help');
  }

  const list = document.getElementById('error-list');
  list.replaceChildren(...errors.map(({ id, msg }) => {
    const li = document.createElement('li');
    const a  = document.createElement('a');
    a.href = '#' + id;
    a.textContent = msg;               // textContent: never inject HTML
    li.append(a);
    return li;
  }));

  summary.hidden = errors.length === 0;
  if (errors.length) summary.focus();
  return errors.length === 0;
}
</script>

    21 · Tools & practiceQuiz

    Check your understanding. Choose an answer, then select Check answer to see whether it is right and why. You can change your answer and check again.

    Question 1 of 7An input has no <label>, only placeholder="First name". What is wrong?

    Placeholder text vanishes when the user types and is not a dependable accessible name. A visible, programmatically associated label is required (3.3.2, 4.1.2).

    Question 2 of 7Payment-method radio buttons are not wrapped in a <fieldset>. Which criterion does this fail?

    1.3.1 requires relationships to be programmatically determinable. Without a fieldset and legend, the options lose the question they answer.

    Question 3 of 7An error is shown only by a red border around the field. What must be added?

    1.4.1 Use of Color and 3.3.1 Error Identification require errors to be described in text. An icon helps, but is not enough on its own, and a hover tooltip is unreachable for keyboard and touch users.

    Question 4 of 7Which attribute enables browser autofill and satisfies 1.3.5 Identify Input Purpose?

    The HTML autocomplete attribute declares each field's purpose. aria-autocomplete is unrelated: it describes how a combobox suggests values.

    Question 5 of 7A custom dropdown traps keyboard focus — the user cannot Tab out. Which criterion does this fail?

    2.1.2 requires that focus can always be moved away from a component using standard keys (or that the user is told how).

    Question 6 of 7Under 2.5.8 Target Size (Minimum), what is the minimum size for a checkbox target without extra spacing?

    2.5.8 (AA, new in WCAG 2.2) requires 24 × 24 CSS pixels, unless undersized targets are spaced so a 24 px circle centred on each does not overlap another. The easiest way to meet it for checkboxes is to make the whole label clickable.

    Question 7 of 7Which login practice fails 3.3.8 Accessible Authentication (Minimum)?

    Blocking paste forces users to transcribe a password from memory or another device — a cognitive function test with no alternative. The other three all help.
