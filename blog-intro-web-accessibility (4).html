Part 1 — Introduction to Web Accessibility

Web accessibility means designing and developing websites, applications, and mobile apps so that everyone can use them — including people with disabilities. It is a fundamental quality requirement, not an optional feature.

A person who cannot see uses a screen reader. A person who cannot use a mouse relies entirely on the keyboard. A person with hearing difficulties needs captions in videos. A user with cognitive difficulties benefits from plain language and predictable navigation.

💡

Key Insight: Accessibility improvements benefit everyone — not just users with permanent disabilities. Someone using a phone in bright sunlight, typing with one hand, or watching a video in a quiet library all benefit from accessible design.

Who Benefits

  • Visual impairment — blindness, low vision, colour blindness. Use screen readers, magnifiers, high contrast modes.
  • Hearing impairment — deaf or hard of hearing. Depend on captions, transcripts, and visual alternatives to audio.
  • Mobility impairment — limited hand or arm movement. May use keyboard only, switch devices, eye tracking, or voice control.
  • Cognitive impairment — dyslexia, attention difficulties, memory conditions. Benefit from clear language and consistent layouts.
  • Elderly users — often experience multiple mild impairments simultaneously.
  • Situational disabilities — bright sunlight on a phone, one hand occupied, noisy environment, slow connection.

Legal Requirements

  • United States: ADA applies to websites and mobile apps. Section 508 mandates accessibility for federal procurement — VPAT documentation required.
  • European Union: European Accessibility Act (EAA) effective June 2025 — mobile apps in banking, e-commerce, and transport must meet EN 301 549.
  • India: RPWD Act 2016, Section 46, mandates accessible ICT.
  • Canada: AODA — Level AA required for private and public sector organisations.

WCAG — Structure & Conformance Levels

WCAG (Web Content Accessibility Guidelines) is the international standard published by the W3C Web Accessibility Initiative (WAI). Current versions: WCAG 2.1 (2018) and WCAG 2.2 (2023).

WCAG is organised into: 4 Principles → 13 Guidelines → 78 Testable Success Criteria at 3 Conformance Levels (A, AA, AAA).

LevelMeaningExampleWho Requires It
A — MustMinimum. Without this, many users cannot access content at all.Images need alt text (SC 1.1.1)Every accessibility standard globally
AA — ShouldStandard legal/commercial target. Most laws require this level.Text must meet 4.5:1 contrast (SC 1.4.3)ADA, Section 508, AODA, EAA, most enterprise procurement
AAA — CanEnhanced. Not required for every page.Contrast enhanced to 7:1 (SC 1.4.6)Specialised services for blind or deaf users
⚠️

To claim WCAG 2.1 AA conformance, a page must pass all Level A and Level AA criteria — not just a selection of them.

POUR — The Four Principles

👁️
Principle 1
Perceivable

Information and UI components must be presentable in ways users can perceive — through sight, sound, or assistive technology.

  • 1.1 Text alternatives for non-text content
  • 1.2 Captions and alternatives for multimedia
  • 1.3 Adaptable content structure
  • 1.4 Distinguishable content (contrast, resize)
⌨️
Principle 2
Operable

UI components and navigation must be operable — users must be able to interact with and navigate the interface.

  • 2.1 Keyboard accessible
  • 2.2 Enough time
  • 2.3 Seizures and physical reactions
  • 2.4 Navigable (skip links, headings)
  • 2.5 Input modalities (touch, voice)
💬
Principle 3
Understandable

Content and the operation of the UI must be understandable — users must be able to comprehend information and predict interface behaviour.

  • 3.1 Readable text
  • 3.2 Predictable behaviour
  • 3.3 Input assistance and error recovery
🔩
Principle 4
Robust

Content must be robust enough to be reliably interpreted by a wide variety of user agents, including assistive technologies — current and future.

  • 4.1 Compatible with current and future tools

Part 2 — How to Test: The Three Layers

Apply all three layers to every element. Skipping any one layer will miss real issues.

#LayerWhat You Check
1Visual CheckUI layout, color contrast, 400% zoom/reflow, no color-only indicators, visible focus indicator
2Keyboard CheckTab order, focus trap, Enter/Space/Escape operability, no keyboard traps anywhere
3Screen Reader + DevToolsSemantic markup, ARIA states, what SR announces vs what you expect, accessibility tree inspection
ℹ️

Automated tools (Axe, WAVE, ANDI) catch approximately 30% of accessibility issues. Manual testing with keyboard, real screen readers, and zoom testing is essential for a complete audit.

Part 3 — 31 Element-wise Testing Guide

Complete practical guide with NVDA, JAWS, VoiceOver, Keyboard & DevTools testing steps for all 31 elements — mapped to WCAG 2.1 success criteria. Pro Tip: Always test with real screen readers using default voice settings on real devices. Browser-based TTS extensions are NOT reliable for WCAG compliance testing.

01 Headings

Headings define the structure and hierarchy of a page. Screen reader users navigate exclusively via headings to find content quickly. A broken heading structure renders navigation impossible.

What to Check
☐Is there at least one H1 on the page?
☐Are all visually styled headings marked up as actual heading elements (h1–h6)?
☐Are headings nested correctly — H1 → H2 → H3, no level skipped?
☐Is H1 used only for the main page title (or primary dialog heading)?
☐For modal dialogs, does the heading start at H2?
☐If role="heading" is used, is aria-level also defined?
☐Are headings used only for structure — not just to make text look big?
How to Test
#MethodWhat to Do & What to Expect
1Visual / ANDIOpen ANDI → Structures → Headings. Review the heading outline tree. Check H1 appears first and no levels are skipped.
2NVDAPress H repeatedly to jump to each heading. NVDA announces: "Heading level 1 [text], heading level 2 [text]". Missing/skipped levels or CSS-only headings will not appear.
3JAWSInsert+F6 opens Headings List. Verify all expected headings appear with correct levels. Use arrow keys to navigate.
4DevToolsF12 → Accessibility tab → Select any heading. Check: role = heading, level = 1/2/3. If a visually large div has no role=heading, it is a failure.
WCAG References
1.3.1 A Info and Relationships — Headings must convey semantic structure programmatically.
2.4.1 A Bypass Blocks — Heading structure allows users to bypass repeated content.
2.4.6 AA Headings and Labels — Headings must be descriptive of their section.
Common Issues
Heading levels skipped (H1 → H3 directly)
Visual headings styled with CSS class only — no semantic tag used
Multiple H1 elements on a single page
Headings used purely for visual styling (bold/large text)
02Images

Images must communicate their purpose to users who cannot see them. The correct alt strategy depends on whether the image is informative, decorative, or functional.

What to Check
☐Is the image informative, decorative, or functional (link/button)?
☐For informative images: does alt text accurately describe the content or purpose?
☐For decorative images: is alt set to empty string (alt="")?
☐For image links or buttons: does alt describe the destination or action?
☐Are images of text avoided? If present, is there a text alternative?
☐For complex images (charts): is a long description provided via aria-describedby or in content?
☐Are informative images loaded via CSS background-image? If so, this is a failure.
How to Test
#MethodWhat to Do & What to Expect
1VisualEnable Windows High Contrast Mode. Images loaded via CSS background-image will disappear — indicating a failure.
2NVDAPress G to jump to the next graphic. NVDA announces: "graphic [alt text]". If NVDA announces the filename (e.g., "banner_img.jpg"), alt text is missing — failure.
3JAWSInsert+F7 opens Graphics list. Each graphic should show a meaningful label. Image-only links with empty alt appear as blank — failure.
4DevToolsF12 → Select the img element → Accessibility tab. Check: name = [alt text], role = img. If name is empty and image is informative, it is a failure.
WCAG References
1.1.1 A Non-text Content — All non-text content must have a text alternative serving equivalent purpose.
1.4.5 AA Images of Text — Use text instead of images of text wherever possible.
Common Issues
alt text says "image of..." or "photo of..." — screen readers already announce "graphic"
Decorative images with descriptive alt text (creates unnecessary noise)
Icon buttons or image links with missing alt text = invisible control
Charts without descriptions — user gets zero data context
03Forms

Forms are the primary interaction model on the web. Poor form accessibility leads to failures at critical points like checkout or registration.

What to Check
☐Does every form field have a visible, descriptive label?
☐Is each label programmatically associated with its control (for/id or aria-labelledby)?
☐Are grouped controls (radio, checkbox) wrapped in fieldset + legend?
☐Are instructions or format hints provided before the field — not just placeholder?
☐Are required fields indicated both visually and programmatically (aria-required)?
☐Are error messages descriptive, actionable, linked via aria-describedby?
☐Is aria-invalid='true' set on fields with validation errors?
☐Does focus move to the first error or error summary on form submission?
How to Test
#MethodWhat to Do & What to Expect
1ANDIOpen ANDI → Focusable Elements → Labels tab. Each field should show its associated label. Fields showing "No label" or "Empty label" are failures.
2NVDAPress F to jump to next form field. NVDA announces: "[label text], edit, required". If only field type is announced with no label — failure.
3KeyboardTab through the entire form. Verify logical order, all fields reachable, Enter submits, Space toggles checkboxes. Verify focus moves to first invalid field after failed submission.
4DevToolsSelect input field → Accessibility tab. Check: name = [label text], role = textbox, required = true/false, invalid = true (if error). Verify aria-describedby points to error message element.
WCAG References
3.3.1 A Error Identification — Errors must be identified and described in text.
3.3.2 A Labels or Instructions — Labels and instructions must be provided for user input.
3.3.3 AA Error Suggestion — Suggestions for correcting input errors must be provided.
4.1.2 A Name, Role, Value — All form controls must expose name, role, and value to AT.
Common Issues
Placeholder text is the only label — disappears on input, SR cannot re-read it
Radio/checkbox groups not in fieldset/legend — group purpose unknown to SR
Generic error "Invalid input" with no guidance on what correct format looks like
Focus not moving to errors after failed submission
04Links & Hypertext

Links are navigation anchors. Their text must communicate destination or purpose clearly — both in context and when read out of context in a links list.

What to Check
☐Is the link text descriptive — does it make sense out of context?
☐Are vague link texts ("Click here", "Read more", "Learn more") avoided?
☐Are bare URLs used as link text?
☐Are links visually distinguishable from body text (not just by color)?
☐Are there any empty links (anchor with no text and no aria-label)?
☐Does the "Skip to main content" link work and move focus correctly?
☐Do links that open new tabs warn users in advance?
How to Test
#MethodWhat to Do & What to Expect
1ANDIANDI → Focusable Elements → Links/Buttons. Review each link's accessible name. Empty links and generic "click here" links will be flagged.
2NVDAPress K to jump between links. Open Links List with Insert+F7 — multiple "Read more" links are a failure.
3JAWSInsert+F7 → Links List. Sort alphabetically — duplicate non-descriptive links will be clearly visible.
4KeyboardTab to each link → Enter → verify correct destination. Tab to any link that opens a new tab — verify advance warning.
WCAG References
2.4.4 A Link Purpose (In Context) — Link purpose can be determined from link text or surrounding context.
2.4.9 AAA Link Purpose (Link Only) — Link purpose can be determined from link text alone.
05Keyboard Accessibility

Every interactive element must be reachable and operable using the keyboard alone. This is the foundation for screen reader users and users with motor impairments.

What to Check
☐Can all interactive elements be reached using Tab and Shift+Tab?
☐Is the focus indicator clearly visible on all focused elements?
☐Does the tab order follow a logical, predictable sequence?
☐Are there any keyboard traps (focus cannot exit an area)?
☐Can dropdowns, expand/collapse, and dialogs be operated via keyboard?
☐Do modal dialogs trap focus correctly and return focus on close?
WCAG References
2.1.1 A Keyboard — All functionality must be operable via keyboard interface.
2.1.2 A No Keyboard Trap — Focus must not be locked within any component.
2.4.7 AA Focus Visible — Keyboard focus indicator must be visible.
Common Issues
outline:none in CSS removes focus ring — invisible focus for keyboard users
Custom dropdown menus that only work on mouse hover
tabindex values > 0 creating unpredictable tab order
06Color & Color Contrast

Sufficient color contrast ensures readability for users with low vision or color blindness. Color must never be the only means of conveying information.

Content TypeAA (Minimum)AAA (Enhanced)
Normal text (< 18pt)4.5:17:1
Large text (≥ 18pt or 14pt bold)3:14.5:1
UI components / graphical objects3:1—
WCAG References
1.4.1 A Use of Color — Color must not be the only visual means of conveying information.
1.4.3 AA Contrast (Minimum) — Text must have minimum 4.5:1 contrast ratio.
1.4.11 AA Non-text Contrast — UI components must have at least 3:1 contrast ratio.
07Tables

Data tables must be marked up with headers, captions, and scope attributes so screen reader users can understand cell relationships when navigating by row and column.

What to Check
☐Is a table used only for actual data (not layout purposes)?
☐Are column and row headers marked with <th> elements and scope attributes?
☐Is a <caption> provided to describe the table purpose?
☐For complex tables, are data cells associated with headers via headers/id?
☐Are sortable column headers using aria-sort attribute?
WCAG References
1.3.1 A Info and Relationships — Table headers and data relationships must be programmatically determinable.
Common Issues
Tables used for page layout — creates incorrect reading order for SR users
Missing <th> elements — SR reads only raw cell data with no column context
Missing <caption> — SR users don't know what the table represents
08Page Titles

The page title is the first thing announced when a screen reader user lands on a page. It must be unique, descriptive, and identify both the current page and the site.

What to Check
☐Does every page have a <title> element in the <head>?
☐Is the page title unique across all pages of the website?
☐Does the title describe the specific page content (not just the site name)?
☐For multi-step forms, does the title reflect the current step?
WCAG References
2.4.2 A Page Titled — Web pages must have titles that describe their topic or purpose.
09Frames & iframes

iframes embed external content. Screen reader users encounter them as separate browsable regions. They must be labeled so users know what is inside before entering.

What to Check
☐Does every <iframe> have a title attribute?
☐Is the title value descriptive and unique on the page?
☐Are iframes containing no meaningful content hidden from AT?
WCAG References
4.1.2 A Name, Role, Value — iframes must have an accessible name via the title attribute.
10Lists

Screen readers announce list type and item count, helping users understand content organization and navigate efficiently.

What to Check
☐Are visual lists marked up as <ul>, <ol>, or <dl>?
☐Are <li> elements placed only inside list elements?
☐Are nested lists correctly structured (list inside a list item)?
☐Are unnecessary single-item lists avoided?
WCAG References
1.3.1 A Info and Relationships — List structure must be programmatically determinable.
Common Issue
Visual bullet points styled with CSS — no semantic <ul>/<li> markup. NVDA does not announce "list".
11Multimedia (Audio & Video)
What to Check
☐Does all pre-recorded audio have a text transcript?
☐Does all pre-recorded video have synchronized captions?
☐Does video with important visual content have an audio description track?
☐Is auto-playing media avoided? If used, does it stop within 3 seconds or provide controls?
☐Are all media player controls keyboard operable?
WCAG References
1.2.2 A Captions (Prerecorded) — Captions must be provided for all prerecorded audio in synchronized media.
1.2.3 A Audio Description or Alternative — Audio description or text alternative for prerecorded video.
1.4.2 A Audio Control — If audio plays for more than 3 seconds, a mechanism to pause or stop it must exist.
12Dialogs & Overlays
What to Check
☐When a modal opens, does focus move inside the dialog?
☐Is focus trapped within a modal dialog (cannot Tab out to background)?
☐When the dialog closes, does focus return to the triggering element?
☐Does the dialog have role='dialog' and a descriptive aria-labelledby?
☐Can the dialog be closed with the Escape key?
☐Is background content hidden from screen readers (aria-hidden on background)?
WCAG References
4.1.2 A Name, Role, Value — Dialogs must expose their role and accessible name to AT.
2.1.2 A No Keyboard Trap — Focus must not be locked inside dialog without a way to exit.
13Reflow & Zoom

Content must reflow and remain fully usable at 400% zoom without requiring horizontal scrolling — equivalent to a 320 CSS pixel viewport width.

What to Check
☐Set desktop viewport to 1280px, zoom browser to 400%. Does content reflow to single column?
☐Is any text or content cut off, overlapping, or hidden at 400% zoom?
☐Does the layout remain functional and usable at high zoom?
WCAG References
1.4.10 AA Reflow — Content can be presented without loss of information at 320 CSS pixels width.
14Status Messages & Dynamic Content

Dynamic page updates — cart counts, form errors, loading indicators, search results — must be announced by screen readers without shifting keyboard focus.

What to Check
☐Are status messages using ARIA live regions or roles?
☐Are success, error, and progress messages announced without moving focus?
☐Is role='status' or aria-live='polite' used for non-critical updates?
☐Is role='alert' or aria-live='assertive' used only for critical messages?
☐Does the live region exist in the DOM on page load (not injected dynamically)?
WCAG References
4.1.3 AA Status Messages — Status messages can be programmatically determined without receiving focus.
15Accordions
What to Check
☐Is the accordion trigger a <button> element?
☐Does aria-expanded accurately reflect open/closed state (true/false)?
☐Does aria-controls reference the id of the content panel?
☐Does focus stay on the trigger button when toggling content?
☐Can the accordion be toggled with Enter or Space keys?
WCAG References
4.1.2 A Name, Role, Value — aria-expanded state must be exposed programmatically.
2.1.1 A Keyboard — Accordion must be fully operable by keyboard.
16Style Sheets & High Contrast Testing
What to Check
☐Is important content delivered via CSS background-image? If so, failure.
☐Does text remain readable when browser zoom is applied?
☐Are .sr-only elements genuinely off-screen (not display:none)?
☐Does the page remain usable in Windows High Contrast Mode?
☐Are focus indicators visible in forced color / high contrast mode?
WCAG References
1.4.4 AA Resize Text — Text can be resized up to 200% without loss of content or functionality.
1.3.1 A Info and Relationships — Structure must not be conveyed through CSS presentation alone.
17Blinking, Moving or Flashing Elements

Flashing content at 3Hz or more can trigger photosensitive epileptic seizures. Moving content must be controllable.

What to Check
☐Is there any flashing content? Does it flash fewer than 3 times per second?
☐Is there any auto-playing animation or moving banner?
☐Is a mechanism provided to pause, stop, or hide any moving content?
☐Does any GIF or CSS animation loop continuously without user control?
WCAG References
2.3.1 A Three Flashes or Below Threshold — Pages must not contain content that flashes more than 3 times per second.
2.2.2 A Pause, Stop, Hide — Moving, blinking, or auto-updating content must have a mechanism to pause, stop, or hide.
18Image Maps
What to Check
☐Does each <area> element have a meaningful alt attribute?
☐Can all hotspot areas be reached via Tab key?
☐Can hotspot links be activated via Enter key?
WCAG References
1.1.1 A Non-text Content — All image map areas must have text alternatives.
2.1.1 A Keyboard — All image map hotspots must be keyboard operable.
19Orientation (SC 1.3.4)

Content must not be restricted to a single display orientation. Users with devices mounted on wheelchairs may have their device fixed in portrait or landscape.

What to Check
☐Does content work in both portrait and landscape orientations?
☐Is there any "Please rotate your device" message blocking content?
WCAG References
1.3.4 AA Orientation — Content must not restrict view to a single orientation unless it is essential.
20Character Key Shortcuts (SC 2.1.4)

Single-character keyboard shortcuts cause accidental activation for speech-input users and users with motor tremors.

What to Check
☐If single-key shortcuts exist, can they be turned off, remapped, or set active-on-focus only?
WCAG References
2.1.4 A Character Key Shortcuts — Single-character key shortcuts must be remappable, disableable, or active-on-focus only.
21Non-Text Contrast (SC 1.4.11)

UI component boundaries and informative graphical objects must have at least 3:1 contrast against adjacent colors.

What to Check
☐Do input borders meet 3:1 contrast against their background?
☐Do button boundaries meet 3:1 contrast?
☐Do focus indicators have 3:1 contrast in all states?
☐Do informative icons (search, warning) meet 3:1 contrast?
WCAG References
1.4.11 AA Non-text Contrast — UI components and graphical objects must have at least 3:1 contrast ratio.
Common Issues
Light gray (#CCCCCC) input border on white background — approximately 1.6:1 ratio, far below 3:1
Focus ring that disappears or is too thin to be visible at required contrast
22Text Spacing (SC 1.4.12)

The page must not break, clip, or overlap content when these overrides are applied: line-height 1.5×, paragraph spacing 2×, letter-spacing 0.12×, word-spacing 0.16×.

What to Check
☐Does text remain readable when all 4 spacing overrides are applied simultaneously?
☐Are there fixed-height containers that clip overflowing text?
WCAG References
1.4.12 AA Text Spacing — No loss of content or functionality when text spacing styles are overridden.
23Pointer Gestures (SC 2.5.1)

Any functionality requiring multipoint gestures (pinch zoom) or path-based gestures (swipe, drag) must have a simple single-pointer alternative.

What to Check
☐Do sliders have + and – increment/decrement buttons as an alternative to dragging?
☐Do carousels have explicit Next/Previous buttons as an alternative to swipe?
☐Do drag-and-drop interfaces have a button-based alternative?
WCAG References
2.5.1 A Pointer Gestures — Multipoint or path-based gestures must have a single-pointer alternative.
24Pointer Cancellation (SC 2.5.2)

Actions should trigger on the Up-Event (releasing), not the Down-Event (pressing). Users must be able to drag away and cancel before releasing.

How to Test
☐Click and hold a button → drag pointer outside → release. The action should NOT have triggered.
WCAG References
2.5.2 A Pointer Cancellation — For single-pointer functionality, at least one cancellation mechanism must exist.
25Label in Name (SC 2.5.3)

The accessible name must contain the exact visible text label. Speech recognition users say exactly what they see — if accessible name differs from visible label, voice commands fail.

What to Check
☐Does the accessible name contain the visible text label verbatim?
☐Does NVDA announce the exact same text that appears visually on the button/link?
WCAG References
2.5.3 A Label in Name — Accessible name must contain the visible text label for interactive controls.
Common Issues
Visible button says "Send" but aria-label='Submit Message' — voice command "Click Send" fails
26Meaningful Sequence (SC 1.3.2)

The DOM order must match the visual reading order. CSS Grid and Flexbox can visually reorder elements — but screen readers follow DOM order.

How to Test
☐Firefox: View → Page Style → No Style. Does the content still make logical sense?
☐NVDA: Press Down Arrow to read page linearly. Does reading order match visual left-to-right order?
WCAG References
1.3.2 A Meaningful Sequence — Correct reading sequence must be programmatically determinable.
27Sensory Characteristics (SC 1.3.3)

Instructions must not rely solely on shape, size, visual location, color, or sound. Example failure: "Click the round button on the right."

WCAG References
1.3.3 A Sensory Characteristics — Instructions must not rely solely on shape, size, visual location, orientation, or sound.
Common Issues
"Click the round green button on the right" — shape + color + location all sensory
"You will hear a confirmation beep" — sound only, no visual alternative
28Multiple Ways to Find Content (SC 2.4.5)

Users must have more than one way to find any page — main navigation, search, site map, breadcrumbs, or related links.

WCAG References
2.4.5 AA Multiple Ways — More than one way must exist to locate a web page within a set of web pages.
29Consistent Navigation & Identification (SC 3.2.3 / 3.2.4)

Navigation menus must appear in the same relative order on every page. Components with the same functionality must have the same accessible name across the site.

WCAG References
3.2.3 AA Consistent Navigation — Navigational menus appear in the same relative order across all pages.
3.2.4 AA Consistent Identification — Components with same functionality have the same accessible name site-wide.
Common Issues
Search icon labeled "Search" on homepage but "Find" on interior pages — breaks voice control
30Language of Page & Parts (SC 3.1.1 / 3.1.2)

The primary language must be declared in the HTML element. When text appears in a different language, that passage must be wrapped in a lang attribute.

How to Test
☐F12 → Elements → Find <html> tag → check lang attribute. Should be: lang='en', lang='hi', lang='fr', etc.
☐Search DOM for foreign language text — verify it is wrapped: <span lang='fr'>Bonjour!</span>
WCAG References
3.1.1 A Language of Page — The default human language of each web page must be programmatically determined.
3.1.2 AA Language of Parts — The human language of each passage in a different language must be programmatically determined.
31Parsing & Code Validity (SC 4.1.1)

Code must be clean and valid so Assistive Technologies can parse it without crashing or misinterpreting the page structure. Duplicate IDs break aria-labelledby and aria-describedby.

What to Check
☐Are there any duplicate IDs on the same page?
☐Are all HTML elements properly opened and closed?
☐Are elements correctly nested (no block-level elements inside inline)?
☐Do aria-labelledby and aria-describedby reference IDs that actually exist?
How to Test
#MethodWhat to Do & What to Expect
1W3C Validatorvalidator.w3.org — Enter the page URL. Check for Duplicate ID errors — critical because ARIA attributes referencing duplicate IDs behave unpredictably.
2DevTools ConsoleRun: const ids = [...document.querySelectorAll('[id]')].map(el => el.id); const dupes = ids.filter((id, i) => ids.indexOf(id) !== i); console.log(dupes)
3NVDAIf NVDA announces nothing, crashes, or reads garbled content on certain elements, invalid HTML may be the cause.
WCAG References
4.1.1 A Parsing — Elements must have correct nesting, unique IDs, and complete tags.
Common Issues
Duplicate id attributes — multiple elements with id='header' breaks aria-labelledby
Unclosed tags creating invalid DOM structure — SR reads incorrect content
aria-describedby pointing to an id that does not exist — announcement fails silently
