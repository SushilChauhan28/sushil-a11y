What is Web Accessibility?

Web accessibility means building websites, applications, and mobile apps so that everyone can use them — including people with disabilities. It is not a nice-to-have. It is a fundamental quality requirement, and in many regions it is also a legal obligation.

A person who cannot see the screen might use a screen reader to have content read aloud. Someone who cannot use a mouse relies entirely on the keyboard. A person with hearing difficulties needs captions in videos. A user with cognitive difficulties benefits from plain language and predictable navigation.

💡

Key Insight: Accessibility improvements benefit everyone — not just users with permanent disabilities. Someone using a phone in bright sunlight, typing with one hand, or watching a video in a quiet library all benefit from accessible design.

The World Wide Web Consortium (W3C) is the international standards body for the web. Within W3C, the Web Accessibility Initiative (WAI) develops accessibility guidelines. Two core standards come from WAI:

  • WCAG (Web Content Accessibility Guidelines) — the primary standard for web content accessibility, currently at version 2.1 and 2.2
  • WAI-ARIA (Accessible Rich Internet Applications) — a technical specification for making dynamic web content and custom UI components accessible to assistive technologies

WCAG — Structure & Overview

WCAG is organised into a clear hierarchy that makes it practical to apply:

ComponentCountDescription
Principles4Perceivable, Operable, Understandable, Robust (POUR)
Guidelines13The broad goals under each principle
Success Criteria78Specific, testable requirements
Conformance Levels3A, AA, AAA — indicating priority and effort

Each Success Criterion (SC) is a testable statement that either passes or fails. For example, SC 1.1.1 requires that all non-text content has a text alternative. Either it does or it doesn't — it is unambiguous.

Conformance Levels (A / AA / AAA)

Every WCAG success criterion is assigned one of three conformance levels.

LevelMeaningReal ExampleWho requires it
AMust be done. Minimum accessibility. Without this, many users simply cannot access content.Images need alt text (SC 1.1.1)Every accessibility standard globally
AAShould be done. The most commonly required level. Most accessibility laws target Level AA.Text must meet 4.5:1 contrast ratio (SC 1.4.3)ADA, Section 508, AODA, EAA, most enterprise procurement
AAACan be done. Enhanced accessibility. Not required for every page.Text contrast enhanced to 7:1 (SC 1.4.6)Specialised services (e.g. services for blind or deaf users)
⚠️

Important: Conformance must be declared for a specific level. To claim WCAG 2.1 AA conformance, a page must pass all Level A and Level AA criteria — not just a selection of them.

The Four POUR Principles

WCAG's 13 guidelines are organised under four foundational principles, known as POUR. Every success criterion maps back to one of these four principles.

👁️
Principle 1
Perceivable

Information and UI components must be presentable to users in ways they can perceive — through sight, sound, or assistive technology.

  • 1.1 Text alternatives for non-text content
  • 1.2 Captions and alternatives for multimedia
  • 1.3 Adaptable content structure
  • 1.4 Distinguishable content (contrast, resize)
⌨️
Principle 2
Operable

UI components and navigation must be operable — users must be able to interact with and navigate the interface.

  • 2.1 Keyboard accessible
  • 2.2 Enough time
  • 2.3 Seizures and physical reactions
  • 2.4 Navigable (skip links, headings)
  • 2.5 Input modalities (touch, voice)
💬
Principle 3
Understandable

Content and the operation of the UI must be understandable — users must be able to comprehend information and predict how the interface behaves.

  • 3.1 Readable text
  • 3.2 Predictable behaviour
  • 3.3 Input assistance and error recovery
🔩
Principle 4
Robust

Content must be robust enough to be reliably interpreted by a wide variety of user agents, including assistive technologies — current and future.

  • 4.1 Compatible with current and future tools

Who Benefits & Why It Matters

Accessibility is often associated only with screen reader users, but the reality is much wider. Disability exists on a spectrum — and many conditions are invisible, situational, or temporary.

  • Visual impairment — blindness, low vision, colour blindness. Use screen readers, magnifiers, high contrast modes.
  • Hearing impairment — deaf or hard of hearing. Depend on captions, transcripts, and visual alternatives to audio.
  • Mobility impairment — limited hand or arm movement. May use keyboard only, switch devices, eye tracking, or voice control.
  • Cognitive impairment — dyslexia, attention difficulties, memory conditions. Benefit from clear language, consistent layouts, and error recovery.
  • Elderly users — often experience multiple mild impairments simultaneously.
  • Situational disabilities — bright sunlight on a phone screen, one hand occupied, noisy environment, slow connection.

Globally, around 1 in 7 people live with some form of disability. That figure does not include the many more affected by situational or temporary limitations. Accessibility is simply good engineering.

Headings

Headings are how screen reader users navigate a page. JAWS and NVDA allow pressing H to jump between headings and 1–6 to jump to specific heading levels. Without a correct heading structure, screen reader users cannot efficiently navigate long pages.

Heading rules:

  • One <h1> per page — the primary topic of the page
  • Heading levels must not skip — h1 → h2 → h3, never h1 → h3
  • Headings must be applied via HTML elements — bold or large text styled with CSS is not a heading
  • Headings must be descriptive — "Section 1" tells users nothing
<!-- ❌ Wrong: heading levels skipped -->
<h1>Dashboard</h1>
<h3>Recent Activity</h3>  <!-- h2 skipped -->

<!-- ✓ Correct: logical hierarchy -->
<h1>Dashboard</h1>
<h2>Recent Activity</h2>
  <h3>Today's Transactions</h3>
  <h3>Pending Approvals</h3>
<h2>Account Summary</h2>

Images & Alt Text

Every image is either informative or decorative. Getting this distinction right is foundational to image accessibility.

  • Informative images — contribute meaningful content not available in surrounding text. Require descriptive alt text.
  • Decorative images — add visual interest only. Must have alt="" (empty string, not missing) so screen readers skip them.
<!-- Informative image -->
<img src="quarterly-chart.png"
     alt="Bar chart showing Q3 revenue by region.
          Asia-Pacific leads at $4.2M, North America at $3.8M.">

<!-- Decorative image -->
<img src="decorative-wave.svg" alt="">

<!-- SVG decorative icon -->
<svg aria-hidden="true" focusable="false">...</svg>

<!-- SVG with meaning -->
<svg role="img" aria-label="Warning: payment failed">...</svg>

Writing good alt text:

  • Describe the content and function — not just the appearance
  • Keep it concise — one to two sentences for most images
  • Do not start with "Image of" or "Picture of"
  • For charts: summarise the key finding, not every data point
  • Never use the filename as alt text

Keyboard Accessibility

Keyboard accessibility is a prerequisite for almost all other forms of assistive technology. Screen readers, switch devices, voice control, and head pointers all rely on the keyboard interaction model.

Core Keyboard Requirements

KeyExpected Behaviour
TabMove focus forward through all interactive elements
Shift + TabMove focus backward
EnterActivate links and buttons
SpaceActivate buttons, checkboxes, and toggle controls
EscapeClose modals, dismiss dropdowns, cancel actions
Arrow keysNavigate within components (tabs, menus, radio groups)
Home / EndJump to first/last item in a widget

Skip Link

A skip link is the first focusable element on every page. It allows keyboard users to bypass the navigation and jump directly to the main content — avoiding having to Tab through every link on every page load.

<!-- First element in body -->
<a href="#main-content" class="skip-link">
  Skip to main content
</a>

<main id="main-content" tabindex="-1">
  <!-- Page content -->
</main>
/* Visually hidden by default, visible on focus */
.skip-link {
  position: absolute;
  top: -100px;
  left: 1rem;
  background: #3730a3;
  color: white;
  padding: 0.75rem 1.5rem;
  border-radius: 4px;
  font-weight: 700;
  z-index: 9999;
  text-decoration: none;
  transition: top 0.2s ease;
}
.skip-link:focus {
  top: 1rem;
}

Focus Indicators

Every focusable element must have a visible focus indicator. Removing focus rings with outline: none without providing an alternative is a WCAG failure. In WCAG 2.2, SC 2.4.11 (Focus Appearance) requires that focus indicators have a minimum area, contrast, and change from unfocused state.

Colour & Contrast

Two separate colour requirements exist in WCAG — one about using colour as the only way to convey information, and one about the actual contrast between foreground and background.

Contrast Requirements

Content TypeLevel AALevel AAA
Normal text (below 18pt or 14pt bold)4.5:17:1
Large text (18pt+ or 14pt bold+)3:14.5:1
UI components & graphical objects (WCAG 2.1+)3:1—
Decorative text, logos, inactive UINo requirement

Colour as the Only Indicator

If a form shows errors only by turning the border red, a user with red-green colour blindness may not notice. Always supplement colour with a secondary indicator:

  • Error state: red border + error icon + descriptive error message text
  • Required fields: asterisk + "required" text in the label, not just a colour change
  • Chart data: different patterns or shapes, not just different colours

Forms

Forms are among the most interaction-heavy components on any website. An inaccessible form means a user cannot register, log in, complete a purchase, or submit a request.

<form aria-labelledby="form-title">
  <h2 id="form-title">Create Account</h2>
  <p id="form-note">Fields marked * are required.</p>

  <label for="full-name">Full name *</label>
  <input type="text" id="full-name"
         aria-required="true"
         aria-describedby="name-error">
  <span id="name-error" role="alert" aria-live="polite">
    <!-- Error message injected here when validation fires -->
  </span>

  <!-- Group related controls with fieldset -->
  <fieldset>
    <legend>Preferred contact method</legend>
    <label><input type="radio" name="contact" value="email"> Email</label>
    <label><input type="radio" name="contact" value="phone"> Phone</label>
  </fieldset>
</form>

Common Form Issues

  • No <label> element associated with input fields
  • Placeholder used as the only label — disappears on input
  • Radio buttons and checkboxes not grouped with <fieldset> and <legend>
  • Error messages not programmatically associated via aria-describedby
  • Generic error messages ("Invalid input") with no guidance on how to fix
  • Required fields indicated only by colour change

Lists

Screen readers announce list type and item count before reading content — "list of 5 items" — which helps users understand structure. Visual lists must be coded as actual HTML list elements.

<!-- Unordered list — order doesn't matter -->
<ul>
  <li>Accessibility audit</li>
  <li>Mobile testing</li>
  <li>Remediation support</li>
</ul>

<!-- Ordered list — sequence matters -->
<ol>
  <li>Run automated scan</li>
  <li>Manual testing with screen reader</li>
  <li>Document findings</li>
</ol>

Common Issues

  • Visual list styled with CSS but using <div> or <p> instead of list elements
  • Definition list (<dl>) used for non-definition content
  • List markup used purely to achieve visual indentation

Page Titles

The page <title> is the first thing a screen reader announces when a page loads. It is also what appears in browser tabs and bookmarks. Without a unique, descriptive title, users cannot determine where they are or quickly switch between tabs.

<!-- ❌ Bad: generic, same on every page -->
<title>Home</title>

<!-- ✓ Good: unique content first, then site name -->
<title>Dashboard — ACME Banking Portal</title>
<title>Shopping Cart (3 items) — MySite</title>
<title>Step 2 of 4: Shipping Details — Checkout</title>

Common Issues

  • Missing page title
  • Inaccurate page title
  • Identical page titles across multiple pages
  • Incomplete page title

Frames & Iframes

Iframes embed external content — maps, videos, payment widgets, social feeds. Screen readers encounter them and announce them as frames. Without a descriptive title, the user has no idea what the iframe contains.

<!-- ❌ Bad: no title, screen reader reads the URL -->
<iframe src="map-widget.html"></iframe>

<!-- ✓ Good: descriptive title -->
<iframe src="map-widget.html"
        title="Office location map — Panvel, Mumbai"
        width="600" height="400">
</iframe>

<!-- SEO-only iframe: hide from AT entirely -->
<iframe src="seo-content.html"
        role="presentation"
        aria-hidden="true">
</iframe>
📌

Do not include the word "frame" in the title — screen readers already announce it as a frame. Write title="Product demo video", not title="Video frame".

Tables

Data tables present relational information in rows and columns. Screen readers navigate tables by announcing header information as cells are read — but only when the table markup is correct. Layout tables should never be used.

<table>
  <caption>Quarterly sales by region — FY 2025</caption>
  <thead>
    <tr>
      <th scope="col">Region</th>
      <th scope="col">Q1</th>
      <th scope="col">Q2</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">Asia-Pacific</th>
      <td>$3.8M</td>
      <td>$4.2M</td>
    </tr>
  </tbody>
</table>

Common Issues

  • Table used for page layout — only data tables should use <table>
  • Missing <caption> or aria-label to describe the table
  • Header cells not marked with <th> and scope
  • Complex tables with merged cells — breaks the regular row-column grid

CSS & Stylesheets — SR-Only, Hidden Content

CSS controls what users see visually, but screen readers follow the DOM — not the visual presentation. Hidden content, invisible text, and focus indicators are all affected by CSS decisions.

/* Screen-reader-only text — visible to AT, hidden visually */
.sr-only {
  position: absolute;
  width: 1px;
  height: 1px;
  padding: 0;
  margin: -1px;
  overflow: hidden;
  clip: rect(0, 0, 0, 0);
  white-space: nowrap;
  border: 0;
}

/* Hide content from both sighted users AND AT */
.hidden-all {
  display: none;           /* removed from layout AND accessibility tree */
  /* OR: */
  visibility: hidden;      /* removed from layout AND accessibility tree */
}

/* ❌ Never do this — removes focus ring without replacement */
*:focus { outline: none; }

/* ✓ Replace with custom focus indicator */
*:focus-visible {
  outline: 3px solid #3730a3;
  outline-offset: 2px;
  border-radius: 2px;
}

Common Issues

  • Informative image defined via CSS background-image — invisible in High Contrast Mode and to AT
  • Focus indicator removed with outline: none without any replacement
  • Hidden content incorrectly still reachable by keyboard

Zoom, Reflow & Viewport

WCAG 1.4.4 requires text to resize to 200% without losing content. WCAG 1.4.10 (Reflow, added in WCAG 2.1) requires content to reflow into a single column at 320 CSS pixels — the equivalent of 400% zoom on a 1280px screen — without requiring horizontal scrolling.

<!-- ❌ Bad: prevents user zoom on mobile -->
<meta name="viewport"
      content="width=device-width, initial-scale=1, user-scalable=no">

<!-- ✓ Correct: allow user scaling freely -->
<meta name="viewport"
      content="width=device-width, initial-scale=1">
/* Use relative units — never fixed px widths on content containers */
.container {
  max-width: 100%;
  width: min(860px, 100%);
  padding-inline: 1rem;
}

/* Use CSS Grid with auto-fit for responsive layout */
.card-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
  gap: 1rem;
}

/* Font sizes: use rem — respects user's browser font settings */
body { font-size: 1rem; }
h1   { font-size: clamp(1.75rem, 4vw, 3rem); }
h2   { font-size: clamp(1.25rem, 3vw, 2rem); }
⚠️

Using user-scalable=no or maximum-scale=1 in the viewport meta tag directly fails SC 1.4.4 Resize Text (AA). Many users with low vision rely on pinch-to-zoom — never block it.

Blinking, Moving & Flashing Elements

Flashing content can trigger photosensitive epileptic seizures. Moving content is disorienting for users with attention difficulties.

The Rules

  • Flashing content must flash fewer than 3 times per second
  • Scrolling or auto-updating content must have a mechanism to pause, stop, or hide it
  • Moving content that starts automatically and lasts more than 5 seconds must be pausable
  • Audio that starts automatically and lasts more than 3 seconds must have a stop/pause control

Use the PEAT tool (Photosensitive Epilepsy Analysis Tool) to test flash rates. Always respect prefers-reduced-motion:

@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}

Multimedia

Audio and video content creates barriers for deaf users, blind users, and users in silent environments. Three techniques address these barriers.

TechniqueWho BenefitsDescription
CaptionsDeaf, hard of hearing, noisy environmentsSynchronised text version of all spoken audio and relevant sounds
Audio DescriptionBlind, low vision usersNarration describing visual-only information in video content
TranscriptDeaf-blind, cognitive disabilitiesFull text version of audio/video content, can be read with braille display
 
<video controls>
  <source src="product-demo.mp4" type="video/mp4">

  <!-- Captions (required for Level AA) -->
  <track kind="captions"
         src="demo-captions-en.vtt"
         srclang="en"
         label="English captions"
         default>

  <!-- Audio description (required for Level AA if visual-only info) -->
  <track kind="descriptions"
         src="demo-audiodesc-en.vtt"
         srclang="en"
         label="Audio description">
</video>

Dynamic Content & ARIA

Single-page applications and dynamic content updates present unique accessibility challenges. When content changes without a page reload, screen readers do not automatically announce the change. ARIA live regions and focus management solve this.

<!-- Polite live region: announces after current speech finishes -->
<div aria-live="polite" aria-atomic="true">
  <!-- Content injected dynamically by JavaScript -->
</div>

<!-- Assertive live region: interrupts speech immediately (use sparingly) -->
<div aria-live="assertive" role="alert">
  Error: Your session has expired. Please log in again.
</div>

<!-- Status message (non-urgent update) -->
<div role="status" aria-live="polite">
  24 results found.
</div>

After a page section updates dynamically, move focus to the new content so keyboard and screen reader users discover it:

// Move focus to the newly loaded section heading
const heading = document.getElementById('search-results-heading');
heading.setAttribute('tabindex', '-1');
heading.focus();

Dialogs, Overlays & Lightboxes

Modals are one of the most commonly misimplemented components. The core requirements are: use role="dialog", trap focus inside the modal, announce the modal title on open, return focus to the trigger on close, and allow Escape to dismiss.

<div role="dialog"
     aria-modal="true"
     aria-labelledby="dialog-title">

  <h2 id="dialog-title" tabindex="-1">Confirm Deletion</h2>
  <p>This action cannot be undone.</p>

  <button>Cancel</button>
  <button>Delete</button>
  <button aria-label="Close dialog">✕</button>
</div>

Focus trap JavaScript: when the modal opens, capture Tab and Shift+Tab events. If focus would move outside the modal, redirect it to the first or last focusable element inside the modal.

Accordions

Accordions must follow the disclosure pattern: heading → button → panel. The button handles expand/collapse state via aria-expanded. The panel uses role="region" and aria-labelledby.

<h3>
  <button aria-expanded="false"
          aria-controls="section-1"
          id="btn-1">
    What is WCAG?
    <svg aria-hidden="true" focusable="false">...</svg>
  </button>
</h3>
<div id="section-1"
     role="region"
     aria-labelledby="btn-1"
     hidden>
  WCAG stands for Web Content Accessibility Guidelines...
</div>
💡

Always put the <button> inside the heading element — not the heading inside the button. <h3><button> preserves heading semantics for screen reader heading navigation.
