Every design system ships components. Buttons, modals, tabs, chips, toolbars — assembled into products used by millions. And yet in almost every audit, the same failures appear across different teams, companies, and tech stacks. Missing aria-expanded. Focus not returning after a modal closes. A contrast ratio of 2.6:1 on an interactive icon. Tab doing the job that arrow keys should do inside a toolbar. These are not edge cases — they are the default state of unreviewed components.

This guide follows the same structure for every component: Common Issues (what was actually found in audits), Best Practices (what the correct implementation requires), and Example Markup (ready-to-use ARIA code).

🧭
Breadcrumbs
Navigation / Wayfinding
Common Issues

No <nav> landmark with aria-label="Breadcrumb" — screen readers cannot identify this as breadcrumb navigation.

Using <ul> instead of <ol> — breadcrumbs are an ordered path; order matters semantically.

Current page item missing — screen readers cannot identify where the user currently is.

Separator character (›, /) included in accessible name — reads as "greater than" or "slash" to screen readers.

Low contrast between separator and background — contrast ratio of 2.6:1 fails WCAG 1.4.11.

Best Practices

Wrap in <nav aria-label="Breadcrumb"> to create a named navigation landmark.

Use <ol> (ordered list) — breadcrumbs represent a hierarchical path where order is meaningful.

Apply to the last item (current page link).

Add separators via CSS ::before pseudo-element with aria-hidden="true", or via a <span aria-hidden="true">.

Example Markup 
<nav aria-label="Breadcrumb">
  <ol>
    <li><a href="/"  aria-label="Home">🏠</a></li>
    <li><a href="/products">Products</a></li>
    <li>
      <a href="/products/guide">Style Guide</a>
    </li>
  </ol>
</nav>
Use <ol> (ordered), not <ul>. Breadcrumbs represent a hierarchical path — the order matters.
🪗
Accordion
Disclosure / Expand–Collapse
Common Issues

Accordion header not wrapped in a heading — breaks semantic structure and screen reader heading navigation.

No visible focus indicator on the accordion header — keyboard users cannot track their position.

Missing aria-expanded — screen readers cannot announce whether the panel is open or closed.

Best Practices

Wrap accordion titles in heading elements (<h2>, <h3>) to maintain page structure.

Place a <button> inside the heading — not the other way around. <h3><button> preserves heading semantics in screen readers.

Use aria-expanded="true/false" and aria-controls="panel-id" on the button.

Use the hidden attribute on collapsed panels — removes content from the accessibility tree entirely.

Example Markup 
<h3>
  <button aria-expanded="false"
          aria-controls="panel-1"
          id="acc-btn-1">
    Timekeeper Details
    <svg aria-hidden="true" focusable="false">...</svg>
  </button>
</h3>
<div id="panel-1"
     role="region"
     aria-labelledby="acc-btn-1"
     hidden>
  Panel content here.
</div>
Use the hidden attribute — not CSS display:none alone — on the collapsed panel. This removes the content from the accessibility tree so screen readers cannot reach it.

Modal & Dialog
Focus Trapping / Critical Interactions
Common Issues

Modal title missing heading semantics (<h2>) — screen reader users cannot understand modal purpose on focus.

Focus not trapped inside modal — Tab key escapes to background content.

Focus not returned to trigger element after modal closes.

Close button has no accessible label — announced as "button" only.

Best Practices

Use role="dialog" on the modal container.

Add aria-modal="true" — instructs screen readers to treat background content as inert.

Label the modal with aria-labelledby pointing to its <h2> heading.

Move focus to the modal heading (tabindex="-1") when it opens. Return focus to the trigger element when it closes.

Trap Tab/Shift+Tab within the modal. Allow Escape key to close.

Example Markup 
<div role="dialog"
     aria-modal="true"
     aria-labelledby="modal-title">

  <h2 id="modal-title" tabindex="-1">Confirm Deletion</h2>
  <p>This action cannot be undone.</p>

  <button>Cancel</button>
  <button>Delete</button>

  <button aria-label="Close dialog"
          onclick="closeModal()">✕</button>
</div>
Modal: trap focus, return focus to trigger on close, use aria-modal="true". Non-modal (cookie banner, chatbot): do not trap focus, use aria-modal="false", move focus to next logical element on close.

Tabs
Tablist / Tabpanel Pattern
Common Issues

Missing role="tablist", role="tab", and role="tabpanel" — screen readers treat tabs as regular links or buttons.

All tabs are focusable via Tab key — should use arrow keys only. Tab should move focus into the tabpanel.

Active tab not communicated — missing aria-selected="true".

Best Practices

Container: role="tablist". Each tab: role="tab". Each panel: role="tabpanel".

Only the selected tab has tabindex="0". All others have tabindex="-1" (roving tabindex).

Left/Right arrow keys navigate between tabs. Tab moves focus into the active tabpanel.

Connect each tab to its panel: aria-controls="panel-id" on the tab; aria-labelledby="tab-id" on the panel.

Keyboard Model
KeyAction
Left / Right ArrowMove focus between tabs
TabMove focus from tab to associated tabpanel
HomeMove focus to first tab
EndMove focus to last tab
Enter / SpaceActivate focused tab (if manual activation)
 
<ul role="tablist" aria-label="Settings">
  <li role="presentation">
    <button role="tab"
            id="tab-1"
            aria-controls="panel-1"
            aria-selected="true"
            tabindex="0">Profile</button>
  </li>
  <li role="presentation">
    <button role="tab"
            id="tab-2"
            aria-controls="panel-2"
            aria-selected="false"
            tabindex="-1">Security</button>
  </li>
</ul>

<div id="panel-1" role="tabpanel" aria-labelledby="tab-1">
  Profile content here.
</div>
<div id="panel-2" role="tabpanel" aria-labelledby="tab-2" hidden>
  Security content here.
</div>

Text Field
Input / Textarea / Form Fields
Common Issues

Placeholder text used as the only label — disappears on input, fails WCAG 1.3.1 and 2.4.6.

Required fields not indicated programmatically — missing aria-required="true".

Error messages not associated with the input — missing aria-describedby pointing to the error element.

Best Practices

Always use a permanent <label for="id"> — never rely on placeholder as the only label.

Mark required fields with both visual indicator (asterisk + text) and aria-required="true".

Link error messages via aria-describedby="error-id". Use role="alert" on the error element to announce it automatically.

Example Markup 
<label for="user-email">
  Email address
  <span aria-hidden="true"> *</span>
</label>

<input type="email"
       id="user-email"
       aria-required="true"
       aria-describedby="email-hint email-err"
       placeholder="e.g. name@company.com">

<p id="email-hint">We will never share your email.</p>

<p id="email-err" role="alert" hidden>
  Enter a valid email address.
</p>
Placeholder text is not a label. It disappears when the user starts typing. Always provide a permanent visible <label> associated via for/id.

Select Dropdown
Native Select / Custom Combobox
Common Issues

Custom dropdown built with <div> elements — no keyboard support, no screen reader semantics.

Missing aria-expanded state — screen readers cannot tell if the dropdown is open or closed.

Listbox placed at the end of DOM, far from the trigger — breaks reading order for screen readers.

Best Practices

Always prefer native <select> — it works out of the box with all assistive technologies.

For custom combobox: use role="combobox", aria-haspopup="listbox", aria-expanded, aria-controls.

Place the listbox immediately after the input in DOM order.

Example Markup 
<!-- Native (always prefer this) -->
<label for="country">Country</label>
<select id="country" name="country">
  <option value="">Select a country</option>
  <option value="in">India</option>
  <option value="us">United States</option>
</select>

<!-- Custom ARIA combobox (only when native won't do) -->
<label id="country-lbl">Country</label>
<div role="combobox"
     aria-labelledby="country-lbl"
     aria-haspopup="listbox"
     aria-expanded="false"
     aria-controls="country-list">India</div>
<ul id="country-list" role="listbox"
    aria-labelledby="country-lbl" hidden>
  <li role="option" aria-selected="true">India</li>
  <li role="option" aria-selected="false">USA</li>
</ul>
aria-labelledby must reference the static label text, not the selected value. For multi-select, add aria-multiselectable="true" on the listbox.

Alert
Live Regions / Status Messages
Common Issues

Alert is present in the DOM on page load — role="alert" only fires when content changes dynamically, not when it already exists.

Success/error toasts not announced to screen readers — missing live region.

Close button labelled "✕" with no accessible name — announced as "button" only.

Best Practices

Start with an empty container in the DOM. Inject content dynamically via JavaScript — this triggers the announcement.

Use role="alert" + aria-live="assertive" for urgent messages (errors, warnings).

Use role="status" + aria-live="polite" for non-urgent messages (save confirmations, info notices).

Example Markup 
<!-- Alert container — starts empty -->
<div id="alert-container"
     role="alert"
     aria-live="assertive"
     aria-atomic="true">
  <!-- Inject content dynamically via JS -->
</div>

<button aria-label="Close alert">✕</button>

<!-- Polite status (non-urgent) -->
<div role="status"
     aria-live="polite"
     aria-atomic="true">
  Form auto-saved at 10:32 AM.
</div>
role="alert" already implies assertive live behaviour — do not add aria-live="assertive" redundantly alongside it. Always start with an empty container.

Autocomplete / Combobox
Search Input with Dynamic Results
Common Issues

Input accessible name derived from placeholder only — disappears on input, not a real label.

Listbox placed at end of DOM — breaks reading order and context for screen reader users.

No live region announcing result count — screen readers cannot tell if or how many results appeared.

Best Practices

Provide a permanent visible <label>; avoid placeholder as the only accessible name.

Input: role="combobox", aria-autocomplete="list", aria-haspopup="listbox", aria-expanded, aria-controls, aria-activedescendant.

Place the listbox immediately after the input in the DOM — never at the page bottom.

Include a visually hidden live region that announces result count (e.g., "5 results. Use arrow keys.").

Example Markup 
<!-- Result count live region -->
<div aria-live="polite" aria-atomic="true"
     class="sr-only">
  5 results available. Use arrow keys.
</div>

<label for="search">Search</label>
<input type="text"
       id="search"
       role="combobox"
       aria-autocomplete="list"
       aria-haspopup="listbox"
       aria-expanded="false"
       aria-controls="search-list"
       aria-activedescendant="">

<ul id="search-list"
    role="listbox"
    aria-label="Search suggestions"
    hidden>
  <li role="option" id="opt-1" aria-selected="false">WCAG 2.2</li>
  <li role="option" id="opt-2" aria-selected="false">ARIA patterns</li>
</ul>

Progress Bar
Dynamic Value Indicator
Common Issues

Progress bar visually updating but missing accessible name or visible label — screen readers cannot describe its purpose.

No role="progressbar" or <progress> element — treated as decorative by assistive technologies.

Best Practices

Prefer native <progress> element for best browser/AT support.

For custom: role="progressbar", aria-valuenow, aria-valuemin, aria-valuemax, aria-label.

For indeterminate loading: omit aria-valuenow and add aria-label="Loading" or aria-busy="true" on the container.

Example Markup 
<!-- Native -->
<label for="upload-progress">Upload progress</label>
<progress id="upload-progress" value="65" max="100">65%</progress>

<!-- Custom -->
<div role="progressbar"
     aria-valuenow="65"
     aria-valuemin="0"
     aria-valuemax="100"
     aria-label="File upload: 65% complete">
  <div style="width: 65%"></div>
</div>
🛠️
Toolbar
Action Group / Rich Editor Controls
Common Issues

All toolbar buttons focusable via Tab — should use roving tabindex with arrow key navigation.

No role="toolbar" — screen readers cannot identify the toolbar as a grouped control region.

Icon-only buttons with no accessible name — announced as "button" only.

Best Practices

Use role="toolbar" on the container and aria-label to describe its purpose.

Implement roving tabindex: only one button holds tabindex="0"; arrows move focus and update tabindex.

Every icon-only button must have an aria-label.

Keyboard Model
KeyAction
TabMove focus to/from the toolbar (one stop)
Left / Right ArrowMove focus between toolbar buttons
HomeMove focus to first button
EndMove focus to last button
Enter / SpaceActivate focused button
 
<div role="toolbar" aria-label="Text formatting">
  <button aria-label="Bold" tabindex="0">
    <svg aria-hidden="true">...</svg>
  </button>
  <button aria-label="Italic" tabindex="-1">
    <svg aria-hidden="true">...</svg>
  </button>
  <button aria-label="Underline" tabindex="-1">
    <svg aria-hidden="true">...</svg>
  </button>
</div>

Datepicker
Date Input / Calendar Widget
Common Issues

Calendar icon is a decorative <span> — not focusable, not keyboard operable.

No date format instruction associated with the input — screen reader users don't know expected format.

Calendar navigation (prev/next month) buttons have no accessible names.

Best Practices

Always prefer <input type="date"> — native browser date picker is accessible in all modern browsers.

Calendar trigger must be a <button> with aria-label, aria-haspopup="dialog", and aria-expanded.

Link date format hint to input via aria-describedby.

Example Markup 
<!-- Native (always prefer this) -->
<label for="start-date">Start date (DD/MM/YYYY)</label>
<input type="date"
       id="start-date"
       aria-describedby="date-hint">
<p id="date-hint">Format: DD/MM/YYYY</p>

<!-- Custom calendar trigger -->
<button aria-label="Open date picker"
        aria-haspopup="dialog"
        aria-expanded="false">
  <svg aria-hidden="true">...</svg>
</button>

<!-- Calendar live region -->
<div aria-live="polite" role="status">
  January 2026
</div>
Use <input type="date"> whenever native is sufficient. The calendar icon must be a focusable, keyboard-operable button — not a decorative <span>.

Universal Header
Site-wide Top Navigation
Common Issues

Skip link implemented as aria-pressed toggle button — should be a plain <a href="#main-content">.

Multiple <header> elements on one page — only one site-wide header per page.

Active page link missing .

Links opening in new tab with no warning — screen reader users unaware of context change.

Best Practices

Skip link: <a href="#main-content"> as the first element in <body>. Target: <main id="main-content" tabindex="-1">.

One <header> per page. Use <nav> inside for navigation regions.

Add to the active navigation link.

For links opening in new tabs, add visually hidden text "opens in a new tab" or use aria-label.

Example Markup 
<!-- Skip link — first element in body -->
<a href="#main-content" class="skip-link">
  Skip to main content
</a>

<header>
  <a href="/" aria-label="Home — Company Name">
    <img src="logo.svg" alt="">
  </a>

  <nav aria-label="Main">
    <ul>
      <li><a href="/">Home</a></li>
      <li><a href="/about">About</a></li>
    </ul>
  </nav>
</header>

<main id="main-content" tabindex="-1">
  Page content here.
</main>
☑️
Checkbox
Binary Toggle / Multi-Select
Common Issues

Custom checkbox built with <div> — no keyboard support, no checked state communicated to screen readers.

Related checkboxes not grouped with <fieldset> and <legend>.

Best Practices

Always prefer native <input type="checkbox"> with an associated <label>.

Group related checkboxes in <fieldset><legend>.

Custom checkbox: use role="checkbox", aria-checked="true/false", tabindex="0", handle Space key.

Example Markup 
<fieldset>
  <legend>Notification preferences</legend>
  <label>
    <input type="checkbox" name="email" checked>
    Email notifications
  </label>
  <label>
    <input type="checkbox" name="sms">
    SMS notifications
  </label>
</fieldset>
🏷️
Chips / Tags
Filter Tokens / Selected Items
Common Issues

Remove button labelled "✕" only — announced as "button" with no context of which chip it removes.

No live region announcing when a chip is added or removed — screen reader users unaware of change.

All chips focusable via Tab — should use roving tabindex with arrow keys.

Best Practices

Each remove button: aria-label="Remove React" (include the chip's name).

Include a polite live region announcing add/remove actions.

Roving tabindex: only one chip has tabindex="0". Arrow keys move focus. After removal, move focus to adjacent chip.

Example Markup 
<!-- Live region for add/remove announcements -->
<div aria-live="polite" aria-atomic="true"
     class="sr-only" id="chip-status"></div>

<ul aria-label="Selected filters">
  <li>
    <span>React</span>
    <button aria-label="Remove React"
            tabindex="0">✕</button>
  </li>
  <li>
    <span>TypeScript</span>
    <button aria-label="Remove TypeScript"
            tabindex="-1">✕</button>
  </li>
</ul>
🔵
Radio Button
Single-Select Group
Common Issues

Radio buttons not grouped in <fieldset> — group name not announced to screen readers.

All radios focusable via Tab — should be one Tab stop; arrow keys select within group.

Best Practices

Always group radio buttons in <fieldset><legend>.

Keyboard: Tab to enter the group; arrow keys to move between options; Tab to exit.

Example Markup 
<fieldset>
  <legend>Preferred contact method</legend>
  <label>
    <input type="radio" name="contact" value="email" checked>
    Email
  </label>
  <label>
    <input type="radio" name="contact" value="phone">
    Phone
  </label>
</fieldset>
🔘
Toggle Button
Pressed State Control
Common Issues

Pressed state communicated via CSS class or visual icon only — screen readers cannot announce the state.

Icon-only toggle button with no accessible label — announced as "button" only.

Best Practices

Use aria-pressed="true/false" to communicate the toggled state — update via JavaScript on click.

Provide a stable aria-label that describes the action, not the current state.

Example Markup 
<button aria-pressed="false"
        aria-label="Bold"
        onclick="this.setAttribute(
          'aria-pressed',
          this.getAttribute('aria-pressed') === 'true'
            ? 'false' : 'true'
        )">
  <svg aria-hidden="true">...</svg>
  Bold
</button>
🔄
Toggle Switch
On/Off Control
Common Issues

Switch state communicated via visual position only — screen readers cannot determine on/off state.

Custom switch built with <div> — not keyboard operable, no ARIA state.

Best Practices

Use role="switch" with aria-checked="true/false" for custom implementations.

Alternatively, use a visually styled native <input type="checkbox"> — natively keyboard operable.

Space key toggles the switch. Provide a visible label.

Example Markup 
<label for="notifications">
  Email notifications
</label>
<button role="switch"
        id="notifications"
        aria-checked="false">
  <span aria-hidden="true">Off</span>
</button>

<!-- Or simpler: styled native checkbox -->
<input type="checkbox"
       id="notif-native"
       class="toggle-switch">
<label for="notif-native">Email notifications</label>

Pagination
Page Navigation Controls
Common Issues

No <nav aria-label="Pagination"> — screen readers cannot identify this as a navigation region.

Current page number not communicated — missing .

"Previous" / "Next" icons with no accessible names.

Example Markup 
<nav aria-label="Pagination">
  <ul>
    <li>
      <a href="?page=1" aria-label="Previous page">‹</a>
    </li>
    <li>
      <a href="?page=1">1</a>
    </li>
    <li>
      <a href="?page=2"
         aria-label="Page 2, current">2</a>
    </li>
    <li>
      <a href="?page=3">3</a>
    </li>
    <li>
      <a href="?page=3" aria-label="Next page">›</a>
    </li>
  </ul>
</nav>

Tile / Card
Content Card / Clickable Container
Common Issues

Entire card made clickable with JavaScript on a <div> — not keyboard operable, no role communicated.

Multiple links inside a card with identical text ("Read more", "Read more") — screen readers cannot distinguish destinations.

Best Practices

Make the card title a descriptive link — the primary interactive element on the card.

Avoid "Read more" links without context. Use aria-label="Read more about iOS Accessibility Testing".

If the entire card must be clickable, use a single <a> wrapping the card content with a full descriptive label.

<article>
  <h3>
    <a href="/blog/ios-accessibility">
      iOS Accessibility Testing 2026
    </a>
  </h3>
  <p>A comprehensive guide to VoiceOver and VPAT...</p>
  <a href="/blog/ios-accessibility"
     aria-label="Read more about iOS Accessibility Testing 2026">
    Read more
  </a>
</article>
🔲
Button
Action Trigger
Common Issues

Icon-only button with no accessible label — announced as "button" with no context.

<div> or <span> used as button — not in tab order, no Enter/Space key handling.

Disabled button with no explanation — users cannot understand why action is unavailable.

Best Practices

Always use native <button> — natively keyboard operable (Enter and Space), focusable, correct role.

Icon-only button: aria-label="Submit form". Icon + text: hide the icon with aria-hidden="true".

Prefer aria-disabled="true" over the disabled attribute — keeps button in tab order so users can discover it.

<!-- Icon only -->
<button aria-label="Close dialog">
  <svg aria-hidden="true">...</svg>
</button>

<!-- Icon + text -->
<button>
  <svg aria-hidden="true">...</svg>
  Save changes
</button>

<!-- Visually disabled but still discoverable -->
<button aria-disabled="true"
        aria-describedby="why-disabled">Submit</button>
<p id="why-disabled" class="sr-only">
  Complete all required fields to submit.
</p>

Navigation Menu
Site Navigation / Submenus
Common Issues

Sub-navigation items not wrapped in <ul><li> — screen readers cannot count items or understand structure.

Link nested inside a button — creates double focus, violates HTML semantics.

Submenu toggle button missing aria-expanded — screen readers cannot announce open/closed state.

Best Practices

Wrap in <nav aria-label="Main">. Use <ul><li> for all navigation items.

Never nest a <a> inside a <button> — use one or the other.

Submenu toggle: <button aria-expanded="false" aria-controls="submenu-id">.

Mark active page: on the current link.

<nav aria-label="Main">
  <ul>
    <li>
      <a href="/">Home</a>
    </li>
    <li>
      <button aria-expanded="false"
              aria-controls="products-submenu">
        Products
        <svg aria-hidden="true">...</svg>
      </button>
      <ul id="products-submenu" hidden>
        <li><a href="/products/a">Product A</a></li>
        <li><a href="/products/b">Product B</a></li>
      </ul>
    </li>
  </ul>
</nav>
🔚
Universal Footer
Site-wide Bottom Navigation
Common Issues

Multiple <footer> elements without differentiation — screen readers cannot distinguish site footer from section footers.

Footer navigation not wrapped in <nav> — not exposed as a navigation landmark.

Best Practices

One site-wide <footer> per page. Use <nav aria-label="Footer"> for footer navigation.

Social media icon links: always include accessible names (aria-label="Follow us on LinkedIn"). Hide icons with aria-hidden="true".

<footer>
  <nav aria-label="Footer">
    <ul>
      <li><a href="/accessibility">Accessibility</a></li>
      <li><a href="/privacy">Privacy Policy</a></li>
    </ul>
  </nav>

  <ul aria-label="Social media links">
    <li>
      <a href="https://linkedin.com/..."
         aria-label="Follow us on LinkedIn"
         target="_blank"
         rel="noopener">
        <svg aria-hidden="true">...</svg>
        <span class="sr-only">(opens in new tab)</span>
      </a>
    </li>
  </ul>

  <p><small>© 2026 Company Name</small></p>
</footer>

Responsive Design
Reflow / Zoom / Orientation

WCAG 1.4.10 (Reflow) requires that content can be presented without horizontal scrolling at 320px equivalent width (400% zoom on 1280px viewport).

Common Issues

Fixed-width containers break layout at high zoom — horizontal scrolling required.

Touch targets smaller than 44×44px — fails WCAG 2.5.5.

Content locked to portrait orientation — fails WCAG 1.3.4.

Best Practices

Use fluid widths: max-width, percentages, clamp(), CSS Grid/Flexbox with wrap.

All interactive elements: minimum 44×44px touch target. Use padding, not just icon sizing.

Never lock orientation with CSS or viewport meta unless absolutely necessary for the content type.

Test at 400% browser zoom on desktop — no horizontal scroll, no content loss.

📋
Master Accessibility Checklist
Pre-Release QA Gate
Semantic Structure
  • Single <h1> per page; heading hierarchy logical and unbroken
  • All landmarks present: <header>, <main>, <nav>, <footer>
  • Skip link as first element in body, pointing to #main-content
  • All lists use <ul>/<ol>/<dl> — no fake lists with dashes
Interactive Elements
  • All interactive elements operable by keyboard only
  • Focus order follows logical reading/visual order
  • No keyboard traps (except deliberate modal trapping)
  • Visible focus indicators on all focusable elements (3px minimum)
  • Touch targets minimum 44×44px
Images & Media
  • All informative images have meaningful alt text
  • All decorative images: alt="" or aria-hidden="true"
  • Videos have captions and audio descriptions where needed
Colour & Contrast
  • All text ≥ 4.5:1 contrast; large text ≥ 3:1
  • UI components and icons ≥ 3:1 against adjacent colours
  • Colour is not the only means of conveying information
Forms
  • All inputs have permanent visible labels — no placeholder-only labelling
